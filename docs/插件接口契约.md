# Kair 插件 API

> 本文定义插件作者可见的契约。与 `core/plugin/Plugins.kt`、`core/plugin/PluginContext.kt`、`core/plugin/Hooks.kt` 保持一致；
> 改动 API 时**必须**同步更新本文（见 `AGENTS.md` 第 6 节）。

---

## 1. 插件形态

```kotlin
interface Plugin {
    /** 反向 DNS 风格稳定 id，如 `dev.kair.plugin.devtools`。 */
    val id: String
    val name: String
    val description: String
    /**
     * 插件版本号，如 `1.8.2`；缺省空串 = 未声明，宿主回退到清单 `version`。
     * 只用于插件列表展示，不参与兼容性检查。
     */
    val version: String get() = ""

    /** 注册贡献点。只做注册，不要启动后台任务或做重 IO。 */
    fun activate(ctx: PluginContext)
}
```

- **静态插件**（有代码的 Kotlin 插件）在**装配期**（`AppContainer` 初始化）一次性安装；
  **动态插件**可在运行期经 `install_plugin` / `uninstall_plugin` 增删，有两种形态：
  **script**（数据 + 脚本，无代码）与 **dex**（`.kplug` 包，代码插件），见第 10 节。
- `activate` 里**只做注册**。需要后台运行的能力，应通过工具 / 面板等贡献点表达。
- 宿主必须能在**没有某插件**时正常工作：插件可降级，不可阻断。
- `version` 显示在插件列表的版本徽标上（`v1.8.2`）。dex 插件在代码里声明时优先于
  清单；未声明则取清单 `version`；内置插件不声明则不显示。

## 2. 贡献点（无序）

通过 `PluginContext` 注册。除注明外，贡献点不互相影响。

> ⚠️ **两套 `PluginContext`**：仓库里有同名两个类型，别搞混。
> - `dev.kair.plugin.api.PluginContext` —— **第三方（dex/`.kplug`）唯一能用的表面**，
>   UI 能力只有声明式的（设置面板 / 槽位）。
> - `dev.kair.app.core.plugin.PluginContext` —— 内置插件用的**内部**上下文，多出
>   `panel` / `action` / `command` / `settingsSection`（直接产出 Compose 元素）。
>
> 下表的「可用范围」列标明谁能用；此前本表把两者混在一起，读起来像第三方也能 `panel()`。

| 方法 | 贡献物 | 去重规则 | 可用范围 |
|---|---|---|
| `tool(tool: Tool)` | 暴露给模型的工具 | 按 `tool.name`，**后注册者胜**（动态插件可覆盖内置工具） | 两者 |
| `panel(panel: PanelContribution)` | 一块 Compose 面板 | 不去重，按 `order` 升序排列 | **仅内置** |
| `settingsPanel(spec: SettingsPanelSpec)` | 声明式设置面板（数值 / 开关 / 文本 / 下拉 / 按钮 / 文件查看编辑），宿主用内置控件渲染 | 按 `id` 去重，按 `order` 升序排列 | 两者 |
| `slot(slot: SlotContribution)` | 声明式 UI 槽位（顶部 / 底部放按钮 / 开关 / 文字 / 面板入口 / 选项弹窗 / 矢量图标），宿主用内置控件渲染 | 按 `id` 去重，按 `order` 升序排列 | 两者 |
| `declareData(path, label)` | 声明插件生成的数据路径（卸载 / 删除时提示并清理） | 按 (插件, 路径) 去重 | 两者 |
| `action(action: ActionContribution)` | 可点击动作 | 按 `id` 去重 | **仅内置** |
| `command(command: CommandContribution)` | 斜杠命令 `/xxx` | 按 `name` 去重 | **仅内置** |
| `settingsSection(section: SettingsSectionContribution)` | 设置页追加分区 | 不去重，按 `order` 升序排列 | **仅内置** |
| `provider(def: ProviderDef)` | 服务商（出现在选择器） | 转发到 `ModelCatalog.register` | 两者 |
| `transport(transport: ProviderTransport)` | Provider 传输层（流式协议解析） | 按 `transport.id` 覆盖 | 两者 |
| `systemPrompt(contributor: SystemPromptContributor)` | 系统提示段落（**有序**） | 按 `order` 升序拼接 | 两者 |
| `contextStrategy(strategy: ContextStrategy)` | 上下文/压缩策略（**单例**） | 后注册者覆盖先注册者 | 两者 |
| `storage(backend: StorageBackend)` | 存储后端（项目 / 会话 / 消息持久化） | 后注册者覆盖先注册者 | 两者 |
| `commandRunner(runner: CommandRunner)` | 命令执行后端（`bash` 工具跑命令） | 后注册者覆盖先注册者 | 两者 |

注册时插件 id 由宿主注入（`panelId` / `pluginId` 字段），插件无需自己填。

### 运行时能力（v8 起可用）

除了「贡献点」，v8 还给了插件三样**运行时**能力。它们的共同点是：不参与请求装配，
因此**不影响缓存前缀**。

| 成员 | 作用 | 缺省（旧宿主）行为 |
|---|---|---|
| `onAgentEvent(handler)` | 订阅只读通知：`AgentEvent.TurnEnd` / `ToolExecuted` / `Compacted` | 空实现，订阅了也收不到 |
| `scope: CoroutineScope` | 插件后台任务作用域（定时器、子智能体、落盘） | 已取消的空调度器：起不来，但不崩 |
| `onDeactivate(handler)` | 卸载 / 删除前回调（停表、落盘状态） | 空实现 |
| `agents: AgentBridge?` | `sessions()` / `send()` / `runSubagent()` / `turnsSince()` | `null`，插件须写 `agents?.` 降级 |
| `dataDir: File?` | 插件私有状态目录（不上设置界面） | `null` |

**事件 vs 钩子的分工**（重要）：钩子参与装配，契约要求**纯函数、无副作用**；事件只告知
「发生了什么」，允许副作用。所以「每 N 回合整理一次」必须挂 `onAgentEvent`，不能拿
`onContext` 数回合。

**事件广播时机**：`TurnEnd` 在回合收尾之后（`runUser` 的 finally，**含被用户中止与出错
的回合**）—— 漏掉中止的回合会让「每 N 回合」的计数永远偏。`turnCount` 数的是**用户回合**，
宿主/插件注入的 system note 不算。处理器在会话线程上同步调用，必须快速返回；抛出的异常
被宿主逐个吞掉，不会带崩会话主循环。

**`agents.send` 的边界**：走正常主循环投一条 system note（只追加历史、不改写已有回合、
**不绕过审批**）；宿主有速率上限（6 条 / 分钟 / 会话）防止「插件发消息 → 回合结束事件 →
插件再发消息」形成环路。返回 `false` 表示会话不存在 / 已关闭 / 被限速。

**`agents.turnsSince` 为什么返回 `TurnDigest` 而不是消息列表**：否则每个插件都要自己写
一遍「跳过思考段 / 跳过工具结果 / 跳过 system note / 截断长文本」，写错就是一次 token
灾难。切分用**用户回合序号**而非消息下标 —— 压缩会重写历史，下标会偏。

**静态选项 vs 动态来源**：`SettingField.Choice` 另有 `source` 字段（`"sessions"` /
`"models"` / `"models_follow_session"`），由宿主在渲染时解析。后两者是模型列表；
`"models_follow_session"` 在首项多一个空值的「跟随当前会话模型」，供「不选 = 继承」
的覆盖类设置使用（空串不会被写回，旧行为保持）。会话与模型列表随用户操作实时变化，
插件在 `activate()` 里拿不到、也不该订阅，写死静态选项等于让插件过期。


### 系统提示段落（有序）

内核只负责按 `order` 稳定拼接（同 `order` 按注册顺序），本身不含任何具体段落。

```kotlin
interface SystemPromptContributor {
    val id: String
    /** 排序权重，小的在前。内置段落取 0/2/5/10/20/30/40；留白便于插件插入其间。 */
    val order: Int
    /** 生成本段正文；返回 null / 空串即不贡献。 */
    fun section(ctx: SystemPromptContext): String?
}

data class SystemPromptContext(
    val cwd: String,
    val tools: List<Tool>,
    /** 设置页「附加系统指令」的正文（全局生效，不分项目）；空串 = 用户没填。 */
    val addendum: String,
    /** 宿主侧真实工作区路径；容器生效时 [cwd] 是容器内工作区路径，读工作区文件必须用本字段。 */
    val workspace: String = cwd,
)
```

- 段内容进入**缓存稳定前缀**，必须是确定性的：不得含时间戳、随机数或随会话变化的内容。
- `cwd` 是**命令实际执行处**（容器生效时为 `/projects/<目录名>`）；需要读工作区文件的贡献点
  必须用 `workspace`（应用进程能直接 `File` 读到的真实路径）。两者在容器未生效时相同。
  内置段落 `dev.kair.prompt.cwd`（order 40）会把两个路径都给模型：容器生效时同时输出
  `<workspace>`（宿主真实路径）与 `<cwd>`（容器内工作区路径），未生效时只输出 `<cwd>`。
  宿主「工作区父目录」bind 挂载于容器 `/projects`，宿主工作区与 `/projects/<目录名>` 是
  **同一批文件**。
- 内置段落：`dev.kair.prompt.preamble`（开场白）/ `.delivery`（交付路径，order 2）/
  `.capabilities`（Kair 能力自述，order 5）/ `.tools` / `.rules` / `.cwd`。
  其中 preamble 是唯一可被「提示词预设」替换的段落；delivery / capabilities / tools /
  rules / cwd 由内核锁定（`SystemPromptBuilder.LockedSectionIds`），覆写一律忽略。
  内置段落的「注册 / 是否锁定 / 面板内置文案」同源于 `BuiltinPromptSections`（`entries`
  里每行一个段落）：新增内置段落只改那一处，内置插件不再手写注册清单。
  `.addendum`（order 30）来自设置页的「附加系统指令」，**全局生效**（不分项目），
  追加在所有段落之后、`<cwd>` 之前；用户没填则为空串，整段不出现。
  它**不是**身份入口：身份（开场白）由「提示词预设」按项目替换。该段在 `entries` 里
  标 `locked = false`，但宿主目前只为 preamble 提供覆写来源，所以预设不会替换它。

### Provider 传输层

内核按 `ProviderDef.transportId` 从 `ProviderTransports` 解析传输层。传输层只负责**协议解析**
（构造请求体、解析流式事件），不关心何时压缩、缓存断点如何放置（那是各自的实现细节）。

```kotlin
interface ProviderTransport {
    /** 稳定标识，如 `TransportIds.OPENAI_CHAT`。 */
    val id: String
    fun stream(request: ChatRequest, config: ProviderConfig): Flow<StreamEvent>
    /**
     * 该端点单张图片允许的最大总像素数（宽 × 高）；`null` = 未声明上限，内核不缩放。
     * 默认实现返回 `null` —— 旧插件不实现也语义正确、链接不失败。
     */
    fun maxImagePixels(config: ProviderConfig): Long? = null
}
```

- **端点上限归传输层声明**：像素上限是**端点属性**，不是核心常量。内置传输层按**真正在调的那个
  端点**声明（LongCat 为 `5_242_880`：`providerId` 命中目录条目，**或** `baseUrl` 的主机名是
  `longcat.chat` 及其子域），其它 OpenAI 兼容端点未声明。只认 `providerId` 会出错 —— 走「自定义」
  填 LongCat 地址、或把预设条目的 baseUrl 改成代理，都是同一个端点却拿到不同上限，后果是内核
  以为「这端点没有上限」，超限图逐字节原样发出去（真机 400 静默不生效）。
  需要限制图片尺寸的第三方端点在自己的 `ProviderTransport` 里覆盖本方法即可。
- **缩放在入库前**：内核在消息入库（`AgentSession.append → ImageDownscaler.attach → store`）时
  按上限等比缩放并写入附件存储，**请求装配期不改写已有回合** —— 历史保持只追加，
  缓存前缀跨回合逐字节稳定。缩放只影响图片 part 的字节，纯文字路径不变。
- **像素缩放是注入的能力，不是内核实现**：内核侧 `ImageDownscaler` 不引 Android 图形类型
  （`ArchitectureGuardTest`），位图解码 / 转正 / 重编码在装配层 `app/app/BitmapImageScaler.kt`，
  由 `AppContainer` 注入每个会话。实现会先按 JPEG 的 EXIF Orientation 转正再缩 ——
  `BitmapFactory` 不应用 EXIF，若不转正就重编码，竖拍照片会变成物理横躺（UI 与模型一起错）。
- 缩放失败（解码异常 / 内存不足）降级为原图上传，**降级落点只有 `store` 一处**，由端点自行拒答，不静默丢图。
- **每条入库决策落一行日志**（tag `KairImage`，`adb logcat -s KairImage`）：`store` 打「命中哪个端点 /
  上限是多少 / 落盘后的真实像素 / 哪条降级」，位图侧打「解码尺寸 / EXIF / 目标 / 采样 / 输出」。
  四条降级（端点没声明上限、读上限抛、缩放器返回 `null`、缩放器抛）在设备上原本**长得一模一样**，
  都是「原样发出去」—— U23 真机 400 查不动就是这个原因。日志接缝由宿主注入
  （`AgentSession(imageLog = ::logImageScale)`），漏接由 `ImageScalingGuardTest` 钉住。

- `ProviderDef` / `ProviderConfig` 只带 `transportId: String`，**没有**枚举分支。
- **内置传输层**（`ProviderTransportPlugin`）：

  | `transportId` | 协议 | 端点 |
  |---|---|---|
  | `TransportIds.OPENAI_CHAT` | OpenAI Chat Completions（含所有兼容端点） | `{base}/chat/completions` |
  | `TransportIds.OPENAI_RESPONSES` | OpenAI Responses API | `{base}/responses` |
  | `TransportIds.ANTHROPIC_MESSAGES` | Anthropic Messages | `{base}/v1/messages` |
  | `TransportIds.GEMINI_GENERATE` | Gemini 原生 | `{base}/v1beta/models/{model}:streamGenerateContent?alt=sse` |

  Gemini 原生传输层使用 `x-goog-api-key` 鉴权，工具 schema 以完整 JSON Schema 走
  `parametersJsonSchema`（legacy `parameters` 只收 OpenAPI 3.0 子集，会吞掉
  `additionalProperties` 等约束）；生成参数里的 Gemini 3 用 `thinkingLevel`，
  2.5 按型号给 `thinkingBudget`（预算表与 pi-ai / DSH 一致）；
  Responses 传输层固定 `store = false`，历史由 Kair 自己回灌。
- **思考签名**：`TextEnd(id, signature)` / `ToolCallStarted(..., signature)` /
  `ReasoningEnd(id, signature, redacted)` 携带服务端签名 —— Gemini 的
  `thoughtSignature`、Anthropic 的 `signature`（`redacted_thinking` 用 `redacted = true`
  且把 `data` 放进 `signature`）、OpenAI 兼容协议的来源思考字段名（如
  `reasoning_content`）、Responses 的 reasoning item 原文。内核分别写进
  `Part.Text` / `Part.ToolCall` / `Part.Thinking` 的 `signature`，下次请求发给**同一来源端点**时
  原样回灌；换端点后不回灌（服务端会拒绝）。来源键是 `(providerId, providerHost, model)` 三元组
  （`providerHost` 为归一化主机名），判据唯一落点 `core/ai/ThinkingReplay.kt` 的 `replaysThinkingTo`；
  消息缺来源字段（老会话）一律不回灌（U76）。这些字段都有默认值，其它传输层忽略即可。
  回灌受模型配置「回传思考内容」开关控制（默认开启，关闭后内核在装配投影里剔除
  `Part.Thinking`），传输层只需如实上报签名，不需要读开关。
- **未注册的 id 降级**为一个 `StreamEvent.Failure`，不抛异常、不硬编码回退到某个实现。
- **段落生命周期（可选上报）**：`TextStart(id)` / `TextEnd(id)` / `ReasoningStart(id, reasoningType)` /
  `ReasoningEnd(id)`。`id` 是 Provider 生成的稳定 part id（Anthropic 的 content block index、
  Responses API 的 `item_id`；Chat Completions 这类没有官方 id 的协议自行合成流内唯一值）。
  上报后内核按 `id` 建立有序段落，「推理 → 正文 → 工具 → 正文」在转录里保持原顺序；
  `ReasoningStart` 的 `reasoningType` 用于区分 `REASONING_TEXT` / `SUMMARY_TEXT`。
  **旧事件仍然有效**：只发 `TextDelta` / `ReasoningDelta` 的传输层照常工作（追加到当前打开的段落），
  新事件是增量契约，不需要一次性迁移。
- **失败的可重试标注**：`StreamEvent.Failure(message, retryable = null, retryAfterMs = null)`。
  内核在传输层之外统一包一层**瞬时失败自动重试**，所有传输层（含第三方插件）共享，插件无需自己实现：
  - 只在**本次尝试尚未产出任何可见输出**时重发 —— 已有 token 流出就不再重发（避免重复输出 / 重复计费 / 内容错位），失败直接上报给用户；退避 1s → 2s（封顶 8s），单回合最多 3 次尝试。
  - `retryable` 省略（`null`）时内核做**结构化判定**：先递归解析错误体（兼容 OpenAI / Anthropic / Google / 中转站裸 `message`），再结合 HTTP 状态码分类。HTTP 408/409/429/≥500、过载 / 限流 / 容量 / 超时视为瞬时；鉴权 / 参数 / 配额（`insufficient_quota` 即使以 429 出现）不重试。显式标注优先生效。
  - `retryAfterMs` 对应服务端 `Retry-After`（仅秒数形式），作为退避下限（封顶 30s）。
  - 于是传输层只需**如实上报失败**：连接期异常建议标 `retryable = true`；链路空闲超时这类「无法区分故障与模型长时间思考」的失败建议标 `false`（重试只会再等一轮同样的超时）。
- **错误文案**：传输层只需按 `HTTP {code}: {body}` 如实上报失败；内核负责提取详情与判定重试，**展示时只给状态码 + 服务端原文，不做中文归类翻译**（归类只服务重试判定），传输层无需自行拼用户文案。

### 上下文/压缩策略（单例能力）

内核只认 `ContextStrategy` 契约，决定「何时压缩、如何摘要」。**同一时刻只有一个策略生效**，
后注册者覆盖先注册者；**没有插件提供时内核降级为不压缩**（长会话可能触发溢出，但不阻断）。

```kotlin
/** 本次压缩的原因：常规压力 / 上下文溢出（端点已拒答且内核独立确认仍超预算）。 */
enum class CompactionTrigger { PRESSURE, CONTEXT_OVERFLOW }

interface ContextStrategy {
    val id: String
    /** 上下文是否已接近窗口上限（窗口减去 reserveTokens）。 */
    fun shouldCompact(contextTokens: Int, contextWindow: Int, settings: CompactionSettings): Boolean
    /** 制定压缩计划；无可压缩内容时返回 null。[trigger] 说明本次为何要压缩。 */
    fun plan(
        messages: List<ChatMessage>,
        settings: CompactionSettings,
        trigger: CompactionTrigger,
    ): CompactionPlan?
    /** 用一次单轮补全生成摘要正文。 */
    suspend fun summarize(
        model: String,
        config: ProviderConfig,
        plan: CompactionPlan,
        customInstructions: String?,
        reserveTokens: Int,
        sessionId: String?,
    ): String
    /** 把摘要与相关文件清单包装成检查点消息正文。 */
    fun wrapSummary(plan: CompactionPlan, summary: String): String
}
```

- **`plan` 的 `trigger`**：内核区分两种时机 —— `PRESSURE`（常规压力，上下文逼近窗口上限）与
  `CONTEXT_OVERFLOW`（端点已拒答，且内核**独立确认**仍超预算）。把「原因」放进契约而不是
  藏在实现内部，是为了让替换策略也能自行决定「溢出时允许丢多少」。内置实现
  `SummarizingContextStrategy` 仅在 `CONTEXT_OVERFLOW` 且常规计划为空时，才退到
  `Compaction.forcedPlan`（丢弃最旧的整轮对话）的有损兜底；正常压力压缩不丢数据。

内置实现 `SummarizingContextStrategy`（插件 `dev.kair.plugin.context`）沿用 pi 的摘要式压缩；
换算法（不同切点 / 摘要格式 / 本地小模型）只需换一个插件，不动内核。

### 缓存可观测（只读）

面板可读取内核提供的 `AppContainer.cacheInspector`，其 `latest: StateFlow<Map<String, CacheReport>>`
**按会话 id 索引** —— 每个会话各自持有最近一次请求的缓存前缀分段、相对上一回合的变化
（未变 / 追加 / 改写）与观测命中率。面板按 `AppContainer.activeSessionId` 取本会话的数据
（否则多会话并发时会显示「最后发出请求的会话」，张冠李戴）。
这是**只读**观测面：插件不得据此改写请求装配（装配器属内核四件套，见 `AGENTS.md` 第 2 节）。
会话关闭时宿主调用 `CacheInspector.remove(sessionId)` 回收该会话的报告（`history` 趋势不受影响）。

### 声明式设置面板（第三方插件也能配置）

`panel(...)` 需要 Compose，只有宿主**内置**插件能用。第三方（动态）插件走**声明式**路径：
`settingsPanel(...)` 只声明「有哪些设置项」的**数据**，宿主用内置控件（开关 / 数值 / 文本 /
下拉 / 按钮 / 文件查看编辑）渲染成一块可点击进入的面板；插件经 `PluginContext.settings`
读写**设置值**（`FileEditor` 例外：它读写的是工作区文件，不经设置存储）。
插件作者因此**不接触 Compose**，UI 也不会与应用的 Compose 版本耦合。

```kotlin
data class SettingsPanelSpec(
    val id: String,
    val title: String,
    val icon: String? = null,
    val order: Int = 100,
    val fields: List<SettingField>,
    /** 是否同时在「设置」页用横线分区渲染（双入口）；默认只在插件详情页显示。 */
    val showInSettings: Boolean = false,
)

/** 一个设置项；key 在插件内唯一，值按 key 落存储。 */
sealed interface SettingField {
    val key: String; val label: String; val description: String?

    data class Toggle(key, label, description = null, default = false, onChange: ((Boolean) -> Unit)? = null)
    data class Number(key, label, description = null, default = 0, min: Int? = null, max: Int? = null)
    data class Text(key, label, description = null, default = "")
    /** 文件查看 / 编辑：宿主用内置编辑器打开工作区的该相对路径（绝对路径原样用）。 */
    data class FileEditor(key, path, label, description = null, readOnly = false)
    data class Choice(key, label, description = null, options: List<ChoiceOption>, default = "")
    /** 按钮动作：点击触发插件自定义逻辑（不是持久化值），onClick 收到本插件的存储。 */
    data class Action(key, label, description = null, buttonLabel: String, onClick: (PluginSettingsStore) -> Unit)
}

/** 按「插件 id + 键」分区持久化，宿主注入实现。 */
interface PluginSettingsStore {
    fun getBoolean(key: String, default: Boolean): Boolean
    fun getInt(key: String, default: Int): Int
    fun getString(key: String, default: String): String
    fun setBoolean(key: String, value: Boolean); fun setInt(key: String, value: Int); fun setString(key: String, value: String)
}
```

- **只暴露数据、不暴露 UI**：自定义 Compose 面板**不支持**（否则第三方会耦合应用 Compose 版本，
  也无法跨版本稳定）。需要更复杂的界面时，用「数值 + 开关 + 下拉 + 按钮」组合表达。
- **落盘**：内置实现 `SharedPrefsPluginSettingsStore` 按键前缀（`plugin_setting_<id>_<key>`）
  存入 `SettingsStore`；删除插件时一并清除。
- `SettingsPanelSpec.id` 与普通面板共用同一导航路由，走 `onOpenPanel`。
- `showInSettings`：置 `true` 时，宿主在「设置」页的插件分区用**横线分隔**渲染同一份声明（与插件详情页构成**双入口**，两处读写同一份数据）；禁用该插件时两处一并消失。内置的「上下文压缩」面板即用此开关。
- `Toggle.onChange`：值落盘后触发，供插件做**副作用**（如按开关实时起停前台服务）；为 null 时只落盘。
- `FileEditor`：插件声明一个**工作区相对路径**（绝对路径原样使用），宿主在面板里放一个「查看 / 编辑」按钮，点开用内置编辑器（与「工作区文件」面板共用同一套 `FileEditorBody`）读写该文件。读写走宿主文件后端（与 `read` / `write` 工具同源，容器在场时可读写 root 文件）；相对路径按**当前活跃工作区**解析。`readOnly = true` 时只查看、不显示保存。
  - 与 `Text` 的分工：`Text` 指的是**插件设置值**（存 `PluginSettingsStore`），`FileEditor` 指的是**工作区里的文件**（文件是唯一事实源）。插件想维护一份自己的文件（如记忆的 `.kair/memory.md`）用本项；若再叠加 `declareData` 声明同一路径，卸载 / 删除时可提示一并清理。

### 声明式 UI 槽位（第三方插件也能放界面）

`slot(...)` 只声明「在哪个区域放哪些控件」的**数据**，宿主用内置控件渲染进会话页
**顶部栏**（`SlotArea.TOP`）或**输入框底部区**（`SlotArea.BOTTOM`）；后者与内置的模型 /
思考强度控件并排、空间不足时可横向滑动。插件作者因此**不接触 Compose**。

```kotlin
data class ToggleSpec(key, label, default = false)
```

- **只暴露数据、不暴露 UI**：同设置面板——插件不与应用的 Compose 版本耦合。想放「SVG 图标」
  就传一段矢量 path 的 `d`，宿主用矢量绘制，**不引入网页 / JS 运行时**。
- **与内置控件共用一套渲染**：底部的「模型 / 思考强度」格子与「上下文占用」圆环，和插件元素
  走的是同一个 `DockChip` / `DockGauge`。所以 `KeyValue` 放出来就是模型切换那种「小标题 + 值」

  收到本插件的 `PluginSettingsStore`（与设置面板共用同一份存储，按 `key`）与 `SlotContext`

- **`Button`（二次确认）**：`confirm` 缺省为 true，点击先弹宿主绘制的确认弹窗，确认后才执行
  `onClick`；弹窗正文由 `confirmMessage` 给出，缺省「确定执行「<label>」吗？」。对齐内置
  「压缩上下文」的交互。不需要确认的插件显式传 `confirm = false`。
- 顶部区渲染进会话页 `TopAppBar` 的 actions 位，渲染为 **48dp 圆形按钮**（对齐内置 `IconButton`：
  固定 48dp 圆、**只显示图标**，`label` / 文本留作无障碍描述；无图标时退回显示文字）；
  底部区渲染进输入框底部区，渲染为 **32dp 圆角 chip**，与内置「模型 / 思考强度」并排、

- **`Panel`（面板导航）**：放在顶部槽位即得到一个「面板入口」按钮，点击后宿主打开
  `panelId`（缺省即 `key`）对应的面板——既可以是插件的 `SettingsPanelSpec.id`，
  也可以是 `PanelContribution.id`。交互与内置的「子智能体 / Linux 会话」入口一致。
- **`Picker`（选项弹窗）**：放在底部槽位即得到一个「小标题 + 当前值」chip，点击弹出
  选项列表（单选）与可选开关列表，行为对齐内置的「模型 / 思考强度」选择器。选中项按
  `key` 持久化（存 `ChoiceOption.value`），开关按各自 `ToggleSpec.key` 持久化；chip 上
  始终回显持久化后的当前值。

## 3. 钩子（有序，可改写核心数据流）

钩子是一串处理函数；每个接收**上一环的产出**，返回替换值，返回 `null` 表示不改写。

| 方法 | 处理函数 | 时机 |
|---|---|---|
| `onInput` | `(String) -> String?` | 用户输入变成消息之前 |
| `onContext` | `(List<ChatMessage>) -> List<ChatMessage>?` | 装配请求上下文时（瞬时，不落盘） |
| `onToolCall` | `suspend (ToolCallHook) -> ToolCallOutcome?` | 工具执行前（**挂起**，供审批等待用户决定） |
| `onToolResult` | `(ToolResultHook) -> ToolResult?` | 工具结果回灌前 |
| `onBeforeProviderHeaders` | `(Map<String,String>) -> Map<String,String>?` | 发出 HTTP 请求前 |

```kotlin
data class ToolCallHook(
    val name: String,
    val arguments: JsonObject,
    val sessionId: String? = null,
    /** 发起调用的会话工作区路径；审批插件据此解析 install_plugin 的相对 source。 */
    val workspace: String? = null,
)

/** 改写后的参数；设置 blockReason 则不执行该工具，并把原因作为错误结果回给模型。 */
data class ToolCallOutcome(val arguments: JsonObject, val blockReason: String? = null)

data class ToolResultHook(val name: String, val result: ToolResult)
```

### 钩子硬性约束

- **纯函数**：无副作用、幂等、只依赖入参。不得在其中做网络 / 磁盘 / 读时间等非确定性操作。
  例外：`onToolCall` 是**挂起**的，允许为等待用户审批而暂停（见下节）；除此之外仍不得有非确定性副作用。
- `onContext` **只能追加**到消息列表末尾；不得改写、删除、重排已有回合（否则破坏缓存前缀，见 `docs/架构与内核边界.md` 第 6 节）。
- 拦截工具调用用 `blockReason`，**不要**抛异常中断会话循环。
- **挂起必须自带超时**：自定义 `tool_call` 钩子若等待用户输入，必须自行超时并返回
  `blockReason`（「未执行」）。宿主 `ApprovalGate` 的超时只保护它自己的闸门，保护不了
  插件里的任意无限等待。
- **取消要传播**：钩子 / 工具里不要吞掉 `CancellationException`（用户按「停止」时它必须
  一路冒到主循环，否则会被当成工具失败并触发模型重试）。

### 工具审批面（`Tool` 接口 + 审批闸门）

工具可声明自身需要用户审批；审批策略由内置插件 `dev.kair.plugin.approval` 挂在
`tool_call` 钩子上**强制执行**（不依赖提示词自觉）：

```kotlin
interface Tool {
    // …name / description / parameters / execute 见第 2 节…

    /** 工具类别：审批面板按类别开关决定是否询问；默认未声明。 */
    val category: ToolCategory get() = ToolCategory.UNSPECIFIED
    /**
     * 工具自身**强制**审批；默认 false。false 不会关闭审批面板的类别开关，
     * 第三方工具未声明 [category] 时由装载层强制为 true。
     */
    val requiresApproval: Boolean get() = false
    /** 审批「同类放行」的归类键；默认取工具名。 */
    val approvalKey: String get() = name
    /** 是否允许「永久放行」；危险操作应为 false，只能逐次 / 逐会话放行。 */
    val approvableForever: Boolean get() = true
    /** 同回合多调用并发执行时本工具可否与其他工具同时跑；默认 false（保守串行）。 */
    val isParallelSafe: Boolean get() = false
    /** 本工具是否**只读**（不产生副作用）；默认 false。 */
    val readOnly: Boolean get() = false
}
```

**`ToolContext` 的宿主注入项**（`execute(args, ctx)` 的第二个参数，`plugin-api` 的类）：
`workspace` / `sessionId` / `commandRunner` / `files` / `isAborted` 之外，U58 起多一项
`var requestCompact: () -> Unit`（默认 no-op）—— 工具调用它 = 请宿主在**下一次请求之前**
压缩上下文（内置 `compact_context` 工具的唯一出口）。注意三点：

- 它是**类体属性**而不是主构造器参数：主构造器的描述符属于插件 ABI，类体里新增带默认值的
  成员对旧插件透明，因此**不提升 `KairApi.VERSION`**；
- 工具**不得**在 `execute` 内同步改写历史：此刻本轮 `tool_call` 已写、`tool_result` 未写，
  压缩切点会拆散这一对（孤儿 `tool_result`，端点直接 400）；
- 用户关掉「自动压缩」时宿主不注入有效回调，工具应返回 `isError = true` 的说明而不是静默成功。

**工具类别（`ToolCategory`）**把「用户关掉某类审批」映射到具体工具，避免第三方工具只能
靠 `requiresApproval = true` 一律弹窗：

| 类别 | 审批面板开关 | 说明 |
|---|---|---|
| `READ` | 无（仅「所有工具都需审批」） | 只读 / 无副作用 |
| `WRITE` | 「文件写入类工具需审批」 | 改文件 / 改持久配置 |
| `DELETE` | 「删除类操作需审批」 | 删除类操作 |
| `EXECUTE` | `bash` / `local_shell` / 「执行类工具需审批」 | 跑命令、委派执行 |
| `UNSPECIFIED` | —— | 未声明：第三方工具**默认需要审批**；内置工具按工具名沿用原规则 |

**默认审批规则**：动态脚本插件的 `manifest.tools[].category` 缺省时，宿主把该工具补成
`requiresApproval = true`；dex 插件通过 `ApiPluginAdapter` 对 `UNSPECIFIED` 的第三方工具
做同样包装。也就是说，**未声明类别 = 每次调用都要审批，且面板无法关掉**；想跟随用户的
类别开关，必须显式声明类别。内置工具与内置插件工具已各自声明类别；仅 `install_plugin` /
`uninstall_plugin` 这类**必须永久强制审批**的宿主工具保持未声明（它们本来就
`requiresApproval = true`，未声明时的行为与旧版一致）。

`isParallelSafe` 的调度语义（宿主保证）：同一回合的多个工具调用里，声明 `true` 的
（只读类、`subagent`、`ask_user` 等）彼此并发；未声明的共用一把锁**按提交顺序串行** ——
写文件 / 跑命令这类「读-改-写」副作用并发会互相覆盖丢失更新。第三方工具除非确认自身
无共享可变状态，否则保持默认。

`readOnly` 供宿主组装**只读子智能体**（`subagent` 工具的 `search` 类型）时过滤工具集：
只保留声明 `true` 的读取类工具（`read` / `ls` / `grep` / `find` / `read_image` / `skill`），
未声明（默认 `false`）的一律视为可能有副作用而不纳入。`coding` 类型（默认）继承全部工具。

`Tool.execute` 的**取消语义**：宿主在工具被取消时先抛出 `CancellationException`，不要把它
包装成 `ToolResult(isError = true)` —— 否则用户按「停止」会被模型理解成「工具执行失败」，
进而重试同一条调用。自定义工具若在内部起子协程，取消时必须一并取消。

内核服务 `ApprovalGate`（`core/agent/Approval.kt`）提供挂起原语与三级放行规则：

- **本次**（`ALLOW_ONCE`）：只放行这一次，不记忆。
- **本会话**（`ALLOW_SESSION`）：按「会话 id + 归类键」放行，会话结束失效。
- **永久**（`ALLOW_ALWAYS`）：按归类键放行，跨会话，由宿主落盘（`SettingsStore.approvalAlwaysAllowed`）。
  工具 `approvableForever = false` 时永久请求**降级**为本会话放行。
- 已被放行规则覆盖的调用直接通过，不再挂起；`DENY` 时以 `blockReason` 阻断并把理由回给模型。
- `install_plugin` / `uninstall_plugin` 由宿主**最后注册**（不可被任何插件覆盖），且
  `approvableForever = false` —— 动态插件等价于任意代码执行，永远需要用户逐次或逐会话确认。
- **挂起与排队**：待批请求按「展示会话 id」索引（`ApprovalGate.pending: StateFlow<Map<String, ApprovalRequest>>`），
  **不同会话的请求互不遮挡、并行待批**；同一会话的并发请求在闸门内**排队**（每会话一把锁），
  不静默拒绝、不互相顶掉卡片。审批面板只取当前会话那一条。
- **超时**：闸门默认等待 3 分钟（`ApprovalGate.DEFAULT_TIMEOUT_MILLIS`），且**从拿到会话锁、
  卡片真正展示时才开始计时**——排队时间不计入超时。用户始终不操作时返回 `TIMEOUT`，调用不执行，
  `blockReason` 告诉模型「审批超时，请询问用户是否重试」—— 不再无限挂起（尤其是没人看着的子智能体）。
- **会话结束**：`ApprovalGate.endSession(sessionId)` 清除该会话的「本会话放行」规则；
  待批请求随会话中止而取消。重开同一会话需重新授权。`ALLOW_SESSION` 规则也可在会话删除时
  按会话前缀清理。
- **子智能体**：`ApprovalRequest.ownerSessionId` 记录顶层父会话，审批卡片显示在父会话
  （以及子智能体详情页）而不是子会话 id 下；嵌套委派会沿 `parentId` 一路向上解析。
  审批面板的「拦截子智能体」开关默认开启，关闭后子智能体的调用完全不走审批（含危险命令）。
- **类别开关**：`Tool.category` 声明 `WRITE` / `DELETE` / `EXECUTE` 的工具，分别受
  「文件写入类工具需审批」「删除类操作需审批」「执行类工具需审批」开关控制；`READ`
  不弹窗（除非打开「所有工具都需审批」）。`bash` / `local_shell` 仍各有独立开关，
  分开拦截两条命令通道。`DELETE` 类别与危险命令一样**不允许永久放行**（只能本会话 /
  逐次，长期放行要去面板关掉该开关）。未声明类别的第三方工具由装载层补成 `requiresApproval = true`，
  面板开关关不掉 —— 这是「声明即可控、不声明即保守」的默认。

**归类键按调用内容生成**（由 `dev.kair.plugin.approval` 组装）：`<approvalKey>:<命令或参数>`
—— shell 工具取 `command` 字段正文（同样命令、不同 timeout 归为同一键），其余工具取完整
参数 JSON 文本。因此放行的粒度是「这一条命令 / 这一组参数」，而非「这个工具」：永久放行
`bash + ls -la` 之后，`ls -l` 或 `rm -rf /tmp` 仍会弹确认。闸门只按原样比对键，不解释其结构。

除工具自身声明与面板开关外，`dev.kair.plugin.approval` 还**默认拦截删除类命令**：`bash` /
`local_shell` 的命令文本（或它经 `sh` / `python3` / `node` / `source` 引用到的脚本文件内容）
命中 `rm` / `rmdir` / `unlink` / `shred` / `find -delete` 时，同样走闸门确认，且
`rememberable = false`（不可永久放行）—— 解除拦截的唯一途径是用户在审批面板关掉对应开关。
此类判定在普通归类键末尾追加**独立后缀** `#danger`，所以「本会话放行」只覆盖这一条危险
命令，不会顺带放行普通命令通道，反之亦然。

## 4. 生命周期与装配

```
AppContainer 初始化
  → 构造 PluginRegistry（内含 HookBus）
  → installAll(内置插件…)
       每个插件：注册 contributions → 写入注册表
                hooks → 追加到 HookBus 链尾
  → DynamicPluginHost.discover()：装载磁盘上的动态插件（跳过已禁用者）
  → resyncTools()：重建执行注册表终序
```

- 安装顺序决定**钩子链顺序**；同名工具**后注册者胜**（动态插件借此覆盖内置工具），
  动作 / 命令 / 设置分区按 id **先注册者胜**。
- 同一 `id` 的（静态）插件重复安装会被忽略。
- `PluginContext` 由宿主构造（`internal`），插件不能自行创建。
- 运行期安装 / 卸载动态插件后，宿主 `resyncTools()` 重建执行注册表终序：
  **内置工具 → 插件贡献工具 → 宿主工具（`install_plugin` / `uninstall_plugin`）**。
  宿主工具永远最后注册，因此**不可被任何插件覆盖** —— 这是动态插件的信任边界。

## 5. 插件 id 约定

- 第三方插件用自己的域名反写，例如 `com.example.plugin.foo`。

## 7. 存储后端

内核只认 `StorageBackend` 契约，实现由插件提供（内置插件 `dev.kair.plugin.storage` 注册本地文件实现 `LocalStorage`；无插件时内核回退到同一实现）。

```kotlin
interface StorageBackend {
    // 项目
    fun listProjects(): List<Project>
    fun createProject(name: String): Project
    fun deleteProject(id: String)
    fun renameProject(id: String, name: String)      // 展示名与工作区目录一起改；调用方先关会话
    fun workspaceDir(project: Project): File          // 必须是真实文件系统路径
    fun workspaceBase(): File? = listProjects().firstOrNull()?.let { workspaceDir(it).parentFile }

    // 会话
    fun listSessions(projectId: String? = null): List<SessionMeta>
    fun createSession(projectId: String, name: String, model: String): SessionMeta
    fun renameSession(id: String, name: String)
    fun touchSession(id: String)
    fun deleteSession(id: String)

    // 消息
    fun appendMessage(sessionId: String, message: ChatMessage)
    fun replaceMessages(sessionId: String, messages: List<ChatMessage>)
    fun loadMessages(sessionId: String): List<ChatMessage>
}
```

- **缓存安全**：`loadMessages` 必须**保序保真** —— 返回顺序与写入顺序一致、字段不丢不改。它是一条会话历史前缀的唯一来源，重排或规范化会改写前缀、让命中率归零。
- **工作区不可换**：`workspaceDir` 面向工具与容器，必须返回真实目录；可替换的只是「项目 / 会话 / 消息」的持久化介质（SQLite / 加密 / 远端同步）。
- **`renameProject`**：展示名与工作区目录**一起改**。调用方必须先关闭该项目的全部会话（会话持有旧路径），并能接受实现决定目录名（内置实现按新名字重新生成）。只改展示名、目录不动会让工具路径失效。
- **`workspaceBase()`**：所有项目工作区的父目录，容器把它整棵挂到 `/projects`。**空项目时也返回**稳定目录（内置实现恒非空），否则「先起持久终端、后建第一个项目」时容器里没有 `/projects`。默认实现从任一项目推导；一个项目都没有时返回 null。

## 8. 命令执行后端与文件访问后端

内核只认 `CommandRunner` 契约，`bash` 工具通过 `ToolContext.commandRunner` 取用；实现由插件提供（内置插件 `dev.kair.plugin.shell` 注册 toybox 实现 `LocalCommandRunner`；无插件时内核回退到同一实现）。

```kotlin
interface CommandRunner {
    val id: String            // 稳定标识，如 `toybox` / `proot-alpine`
    val displayName: String
    val description: String

    /** 命令实际在容器内执行时非空；内置容器返回项目根挂载点 `/projects`。不进容器时为 null。 */
    val containerWorkspacePath: String? get() = null

    /**
     * [workspace] 在容器内的真实路径（`bash` 的 cwd）；进不去容器时为 null。
     * 默认回退到 [containerWorkspacePath]（旧实现把工作区直接挂到固定点），
     * 内置容器覆盖为 `/projects/<目录名>`。
     */
    fun containerWorkspacePathFor(workspace: File): String? = containerWorkspacePath

    /** 在 workspace 目录下执行命令，返回原始输出、退出码与超时标记。 */
    suspend fun run(command: String, workspace: File, timeoutSeconds: Long?): CommandOutput
}

data class CommandOutput(val output: String, val exitCode: Int, val timedOut: Boolean = false)
```

- **职责边界**：后端只负责「把命令跑起来 + 交回原始结果」。输出截断、超时文案、错误标记都由 `bash` 工具处理。
- **输出缓冲必须有界**：`LocalCommandRunner` 在**读取阶段**就只保留尾部（`TailTextBuffer`，
  默认 256K 字符），而不是先全量累积再截断；第三方后端也必须自行限流，不能无限
  `readText()` 累积 —— 长命令 / 大日志会直接把进程打爆。
- **工作区契约**：`workspace` 是宿主机上的真实目录，容器实现应把它（或它的父目录）bind 到容器内路径，而不是复制。
- **`containerWorkspacePathFor(workspace)`**：装配层据此决定系统提示 `<cwd>` 的值 —— 进容器给容器内工作区路径（内置容器为 `/projects/<目录名>`），不进容器给宿主真实路径。默认实现返回 `containerWorkspacePath`，旧插件语义不变；内置容器把工作区**父目录**挂到 `/projects`，所以覆盖它。另把宿主真实工作区路径填入 `SystemPromptContext.workspace`，供读工作区文件的提示段使用（见上文 SystemPromptContributor 一节）。本地 shell 后端（含容器未就绪时的回退）一律返回 `null`，避免把模型引向容器内不存在的宿主路径。容器实现按「rootfs 就绪 / 已拿到 Root」判定。
- **`containerWorkspacePath`**：只作「这条通道真的进了容器」的非空标记（内置容器返回 `/projects`），**不要直接当 cwd**；cwd 用 `containerWorkspacePathFor`。
- **这是 proot 的接入点**：proot 工作区（`docs/架构与内核边界.md` 第 9 节）就是本契约的一个实现 —— 插件里 `ctx.commandRunner(ProotCommandRunner(...))` 即可接管 `bash`，内核与工具不改。
- **不进提示词**：`bash` 工具的 `description` 属于缓存稳定前缀，只描述稳定事实，不写「当前是哪个后端」。

### 8.1 文件访问后端（`FileBackend`）

`read` / `write` / `edit` / `ls` / `grep` / `find` 六件文件工具不再直接用 `java.io.File`，
统一经 `ToolContext.files` 取用的 `FileBackend` 契约做 I/O，与 `CommandRunner` **对称**：

```kotlin
interface FileBackend {
    fun resolve(path: String): String
    suspend fun exists(path: String): Boolean
    suspend fun isDirectory(path: String): Boolean
    suspend fun readText(path: String): String
    suspend fun size(path: String): Long?               // 无法高效获知时返回 null（默认实现）
    suspend fun writeText(path: String, content: String)   // 自动建父目录，UTF-8，字节精确
    suspend fun list(path: String): List<DirEntry>
    suspend fun mkdir(path: String)                        // 建目录（含父目录）
    suspend fun delete(path: String)                       // 删除文件/目录（目录递归）
    suspend fun copy(from: String, to: String)             // 复制（目录递归、覆盖）
    suspend fun move(from: String, to: String)             // 移动 / 重命名
    suspend fun walk(root: String, skipDirs: Set<String>): List<String>
    fun relative(root: String, path: String): String
}

data class DirEntry(val name: String, val isDirectory: Boolean)
```

- **`LocalFileBackend`**（默认）：与应用自身权限一致，直接用 `java.io.File`，行为与引入接缝前**逐字节相同**。
- **`ContainerFileBackend`**（容器在场时由宿主注入）：读/写先走本地快路径，本地**够不到 / 改不动**（EACCES、不存在）再**升级到容器内**执行 —— 容器以 root 跑，于是 `bash`（root）建的文件 / 目录、以及容器独有的路径（如 `/etc`）都能被文件工具访问。变更类操作（`mkdir` / `delete` / `copy` / `move`）同策略：本地执行后复查结果，未达成再升级到容器内执行。
  - **写入自愈**：本地写失败时先尝试「同目录临时文件 + rename 覆盖」。替换 root 属主的文件只需要**目录可写**（unlink / rename 看目录权限，不看文件权限），产物因此归应用所有、权限正常，之后本地读写无需再升级；目录也不可写才升级到容器 root，并在落盘后 `chmod 644` —— 否则 root 属主的 600 文件会让依赖 `java.io.File` 的插件（如记忆插件）读不到，只能每次升级。符号链接不做替换（rename 会改变链接语义），仍走容器升级路径。
  - **为什么不许「顺手进容器」**：每次升级都要起一个容器进程 —— **chroot 通道是 `su -c sh <script>`，即一条 `su` = Root 管理器一条授权通知**（proot 通道不调 `su`，用 ptrace 假装 root；见 `RootCommandRunner` / `ProotCommandRunner`）。同一代成本在用户侧就是「面具又弹了」。所以「本地能干就绝不进容器」是硬性要求，不是可选优化：读文件、列目录、删应用自己属主的文件都是本地快路径，只有本地**看不到 / 改不动**（root 属主、容器独有路径）才升级。
  - **路径映射**：工作区内的路径转**相对路径**（容器与本地回退两种模式下 cwd 都是工作区，相对路径两边都成立）；工作区外保持原样（`/sdcard` 两边都可用）。
  - **字节精确写**：内容经 base64 走管道落盘并按块切分（heredoc 会多补换行、单引号 `printf` 扛不住任意内容、单条命令还有参数长度上限）。
- **注入时机**：宿主 `AppContainer` 每次请求实时解析 —— 有插件提供 `CommandRunner`（容器在场）时注入 `ContainerFileBackend`，否则 `LocalFileBackend`。插件热变更即时生效。
- **`size` 的语义**：返回 `null` 表示「无法高效获知」。`LocalFileBackend` 直接 stat；
  `ContainerFileBackend` 本地可见时走本地，否则在容器内 `stat -c %s`（不支持则返回 null）。
  调用方（`read` / `grep` / 文件编辑器）用它在**读取前**拒绝超大文件 —— 后端返回准确大小
  就能避免把整个文件读进内存，第三方后端应尽量提供。
- **UI 复用**：宿主 `AppContainer.fileBackend(workspace)` 把同一后端暴露给 UI —— 内置插件 `dev.kair.plugin.workspacefiles` 的「工作区文件」面板据此在应用内浏览 / 预览 / 编辑工作区文件。因私有目录对外部 App 不可见，浏览器只能自建（不走系统文件管理器），也因此不需要任何存储授权。容器在场时，`bash`（root）建的文件同样能在面板里读到。
- **不进提示词**：文件工具的 `description` 同样只描述稳定事实，不写「当前走哪个后端」。

### 8.2 图片与附件（模型可见的图片）

工具把图片交给模型，走 `ToolResult.images: List<Part.Image>`（`read_image` 即如此）：

```kotlin
data class ToolResult(
    val content: String,
    val isError: Boolean = false,
    val images: List<Part.Image> = emptyList(),
)

data class Part.Image(
    val base64: String? = null,       // base64 本体（不含 `data:` 前缀）
    val url: String? = null,          // 远程 / 本地图片 URL
    val mediaType: String = "image/png",
    val ref: AttachmentRef? = null,   // 内容寻址引用；由内核落地后回填，插件一般不用管
)

data class AttachmentRef(
    val sha256: String,
    val mediaType: String = "image/png",
    val width: Int = 0,
    val height: Int = 0,
)
```

- **插件只给内联 `base64`（或 `url`）即可**：内核在消息进入历史时把内联图片转成内容寻址
  引用（回填 `ref`），会话日志因此**只存引用、本体另存附件存储**；请求装配时再按引用水合回
  base64 发给模型。插件**无需**碰附件存储，也**不要**自行构造 `ref`。
- **缓存安全**：内容寻址 → 同一字节永远得到同一 sha，水合出的 base64 逐字节稳定；旧会话内联
  base64（`ref == null`）原样兼容。详见 `docs/架构与内核边界.md` 第 6.4 节。
- `read_image` 之外的自定义图像工具（如动态 dex 插件）同样只需返回 `Part.Image(base64 = …)`。

## 9. 技能（Skills）

技能是一份 `SKILL.md` 文档，采用**渐进式披露**：只有「名称 + 描述」进入系统提示
（缓存稳定前缀），正文由模型按需通过 `skill` 工具读入（工具结果在请求**尾部**追加，
不破坏前缀）。

### 格式

```
skills/<name>/SKILL.md

---
name: my-skill
description: When the model should use it
---
Full instructions...（正文，frontmatter 可省略——此时以目录名为技能名）
```

### 注册与查找（`core/skills`）

- 技能根：`<storageRoot>/skills/`（内置插件 `dev.kair.plugin.skills` 注册），
  动态插件可经 `manifest.skills` 贡献自己目录内的技能根。
- 内置技能（如 `plugin-authoring`）先于根目录加入；**同名时先加入者胜**。
- `find` 按名称**不区分大小写**；`list` 稳定排序（缓存安全）。

### 系统提示索引段

`SkillsContributor`（`order = 15`，位于工具清单与规则之间）只列名称与描述；
技能集合为空时整段不贡献。索引内容确定性、排序稳定，满足缓存前缀要求。

## 10. 动态插件（运行期热插拔）

动态插件是 agent / 用户在运行期安装的插件形态，分两种 `kind`：

> 如果能力已经有现成的 **MCP 服务器**，优先安装 MCP（`mcp_manage`），不必写插件：
> 远端工具以 `mcp__<server>__<tool>` 进入工具集，见 `docs/架构与内核边界.md` 9.10。

- **script**（默认）：**纯数据 + 脚本**。宿主解释清单注册贡献点，不加载任何代码，
  不受 Android 可写目录执行限制，也不受宿主编译期耦合影响。
- **dex**：**代码插件**（宿主用 `DexClassLoader` 装载 `classes.dex`，能力上限更高：可替换
  单例后端、提供传输层），见 10.4。打包成 `.kplug` 是两种 `kind` **共用**的分发格式，
  与「是否编译」无关。

### 10.1 目录与清单（script）

```
  my_tool.sh               # tools[].script 引用的脚本
  skills/<name>/SKILL.md   # 可选（manifest.skills 指向时生效）
```

```json
{
  "id": "my-plugin",
  "name": "My Plugin",
  "description": "…",
  "version": "0.1.0",
  "kind": "script",
  "minKairVersion": "1.0.0",
  "maxKairVersion": "1.9.9",
  "tools": [{
    "name": "my_tool",
    "description": "What the tool does, shown to the model",
    "script": "my_tool.sh",
    "parameters": { "type": "object", "properties": {}, "required": [] },
    "snippet": "one-liner for the system prompt tool list",
    "guidelines": ["a behavioral rule for the model"],
    "category": "write",
    "approvableForever": true,
    "timeoutSeconds": 30
  }],
  "prompts": [{ "id": "my.prompt", "order": 50, "text": "Static system-prompt section." }],
  "skills": "skills",
  "settingsTitle": "My Plugin 设置",
  "settings": [
    { "key": "enabled", "label": "启用", "type": "toggle", "defaultBool": true },
    { "key": "retries", "label": "重试次数", "type": "number", "defaultInt": 3, "min": 0, "max": 10 },
    { "key": "endpoint", "label": "端点", "type": "text", "defaultText": "https://example.test" },
    { "key": "mode", "label": "模式", "type": "choice", "defaultText": "fast",
      "options": [{ "value": "fast", "label": "快速" }, { "value": "safe", "label": "稳妥" }] }
  ]
}
```

- `parameters` 是 JSON Schema 对象，缺省为空对象 schema。
- `category` 取 `read` / `write` / `delete` / `execute`，决定该工具跟随审批面板的哪个
  类别开关；**缺省时该工具每次调用都需要审批**（用户无法在面板关闭）。详见第 3 节
  「工具类别」。
- `requiresApproval` 通常**不需要写**：默认 `false`，且 `false` 不会关闭任何审批——它只表示
  「工具自身不强制审批」。只有需要「即使用户关掉对应类别开关、也必须每次确认」时才写
  `true`；危险工具再配 `approvableForever: false`。
- `version` 是插件自身版本（缺省 `0.1.0`），显示在插件列表的版本徽标上；dex 插件
  可在代码里声明 `Plugin.version` 覆盖它（优先）。
- `minKairVersion` / `maxKairVersion` 是**可选**的宿主应用版本范围（点分
  `major.minor.patch`，可带 `-pre` 后缀，两端**含**），缺省表示不限制。宿主在安装前
  比对自身版本：低于下限报「版本过低」、高于上限报「版本过高」。dex 插件另有
  `targetApi`（前向兼容：不得高于宿主 `KairApi.VERSION`）。这些检查与「插件 id 是否
  与内置插件冲突」一起构成安装闸门，见 10.3。
- `prompts[].text` 是**静态常量**，进入缓存稳定前缀（天然确定性）。
- 工具 `name` 与内置工具同名时**替换**内置工具（后注册者胜）。
- `settings[]` 声明式设置面板：`type` 为 `toggle` / `number` / `text` / `choice`
  （对应 `defaultBool` / `defaultInt` / `defaultText`，`number` 可带 `min` / `max`）；
  宿主用内置控件渲染、按 `key` 持久化。面板标题取 `settingsTitle`，缺省用 `name`。
  `settingsShowInSettings: true` 时该面板同时在「设置」页显示（双入口，见第 2 节）。
  脚本工具经 `KAIR_SETTINGS` 读到这些值的 JSON（见 10.2）。**按钮动作**与**文件查看 / 编辑**
  只能由 dex 插件用 SDK 的 `SettingField.Action` / `SettingField.FileEditor` 声明
  （前者需代码回调、后者需宿主文件后端），清单不支持。

### 10.2 脚本契约

脚本经**当前命令执行后端**以 `sh -c` 运行（proot 就绪时即跑在 Alpine 里）：

- 环境变量 `KAIR_TOOL` = 工具名，`KAIR_ARGS` = 调用参数（JSON 对象字符串），
  `KAIR_SETTINGS` = 本插件设置值的 JSON（`manifest.settings` 声明时才有）。
- stdout + stderr 作为工具结果回给模型；退出码非 0 视为错误。
- 参数引用一律经单引号转义（`shellQuote`），防注入。

### 10.3 安装 / 卸载（`DynamicPluginHost`）

1. agent 用文件工具把插件写到工作区目录（默认 `plugins/<id>/`），
   或下载一个 `.kplug` 包文件；
2. 调 `install_plugin { "id": …, "source": … }` —— **需审批且不可永久放行**；
   宿主校验清单（id 一致、脚本/dex 存在、目录名无穿越、zip 条目无路径穿越）后
   复制到持久插件目录并装载。审批弹窗会展示**预览摘要**（插件会带来 / 替换什么）；
3. 装载前做**兼容性检查**（`PluginCompatibility`，见 10.1）：`targetApi` 前向兼容、
   `minKairVersion` / `maxKairVersion` 版本范围、与内置插件 id 冲突。不兼容时按
   「设置 → 插件兼容严格模式」开关处理：**严格模式**（默认）直接拒绝，UI 捕获
   `PluginIncompatibleException` 列出具体原因并提供「强制安装」旁路（用户自行承担
   风险）；**非严格模式**仅告警放行，安装结果文案附带原因；
4. `uninstall_plugin` **停用**：回收贡献点 + 记 `plugins/disabled.json`，**文件保留**，
   重启后 `discover()` 跳过；重新 `install` 即恢复（即插件页的「已停用」区）。
5. 重装（升级）先卸载旧贡献点再装载，不残留、不重复。
6. `DynamicPluginHost.delete(id)` **删除**：回收贡献点 + 删除磁盘上的插件目录 / `.kplug`
   包 + 从 `disabled.json` 移除（并清其设置键），**不可恢复**。只在插件页（UI）提供，
   不经 agent 工具，避免模型误删。

**插件数据声明（`declareData`）**：插件可在 `activate()` 里声明自己生成的数据路径
（工作区相对或绝对），如 `ctx.declareData(".kair/memory.md", "记忆文件")`。宿主记录这些
声明；**删除**插件时若插件声明过数据，插件页先弹确认框列出待删项，用户确认后连同数据
一并删除（不进回收站）。相对路径相对**当前活跃工作区**解析。声明是可选的——未声明数据
的插件删除流程不变。想保留数据的用户应改用「停用」而不是「删除」。

**卸载（停用）vs 删除**：前者是「回收贡献点、保留文件、可再启用」，后者是「连同文件一并
移除」。插件页同时提供「停用 / 启用 / 删除」三个入口，并单列「已停用」区展示可再启用者。

**卸载回滚语义**：卸载回收该插件的全部贡献点（工具 / 提示段 / 技能根）；
单例能力（命令后端 / 存储 / 压缩策略）按**提供者历史栈**回滚到上一个提供者
（没有则回退内核默认实现），因此「社区插件替换原装后端 → 卸载 → 还原」
**无需重启**。dex 插件的类本身驻留内存直到进程重启（与游戏 mod 相同：
禁用即失效，类不卸载）。

**热发现（默认开启，无开关）**：`install` / `uninstall` 后宿主触发 `resync` 重建执行
注册表终序，且各贡献点查询均为实时；`AgentSession` 的 `contextStrategyProvider` /
`commandRunner` / `filesProvider` 与系统提示都**每次请求重新解析**而非构造时固化 ——
因此**已存在的会话无需重建**即可在下一回合看到新插件的工具 / 提示段 / 策略。代价是
该会话此前的**缓存前缀失效**（插件变更会改掉系统提示 / 工具列表字节，`CacheInspector`
会如实显示命中率回落）；未发生变更时前缀仍逐回合稳定。

### 10.4 `.kplug` 包（script 与 dex 通用）

`.kplug` 只是「插件目录的 zip」，**两种 `kind` 都能打包**，与是否编译无关。
包根必须直接放 `manifest.json`（不得再套一层 `<id>/` 目录）：

```
my-plugin-0.1.0.kplug
  manifest.json      # kind: "script" 或 "dex"
  my_tool.sh         # script：tools[].script 引用的资产、skills/ 等
  skills/<name>/SKILL.md
  classes.dex        # dex：插件代码（可选脚本 / 技能等资产）
  LICENSE            # 可选
```

- 打包命令：在插件目录**内部**执行 `zip -r -X ../<id>-<version>.kplug .`，
  或逐项列出文件（不写目录条目，与社区包保持一致）。
- 文件名约定 `<id>-<version>.kplug`，`manifest.version` 与之保持一致。
- 只打包运行期资产：不要带设置值、缓存、生成物、`.git`。
- `.kplug` 对用户是**一键安装**入口（插件页「安装」→ 文件选择器）；该路径是用户显式
  操作，不经 agent 侧审批。`install_plugin { "source": … }` 要求文件名以 `.kplug`
  结尾才按 zip 解包，否则按目录处理并失败。

#### dex 插件

```json
{
  "id": "com.community.myplugin",
  "name": "My Plugin",
  "description": "…",
  "kind": "dex",
  "entryClass": "com.community.myplugin.MyPlugin",
  "targetApi": 1
}
```

- `entryClass` 必须实现 `dev.kair.plugin.api.Plugin`（`:plugin-api` 模块）。SDK 表面 =
  工具 / 传输层 / 系统提示 / 声明式设置面板（`settingsPanel` + `settings`）/
  声明式 UI 槽位（`slot`，见第 2 节）/ 数据路径声明（`declareData`，见 10.3）/
  三个单例后端 / 五个钩子；**不含 Compose**，
  自定义 UI 面板不开放给第三方。且有无参构造。
- **打包规则**：插件编译时依赖 `:plugin-api`，但**不得**把契约类打进自己的 dex
  —— 宿主按父委派提供 `dev.kair.app.core.*` / `dev.kair.plugin.api.*` /
  `kotlinx` 系列的类；重复打包会触发 `ClassCastException`。
- `targetApi` 高于宿主 `KairApi.VERSION` 时拒绝装载（前向兼容）。**v2** 起支持声明式设置
  面板，**v3** 起支持声明式 UI 槽位（`slot`），**v4** 起槽位新增面板导航 / 选项弹窗
  （`SlotElement.Panel` / `SlotElement.Picker`）并新增数据路径声明（`declareData`），
  **v5** 起设置面板新增 `SettingField.FileEditor`（文件查看 / 编辑），**v6** 起槽位交互回调
  新增会话上下文（`SlotContext`：会话 id + 工作区）且 `SlotElement.Button` 新增
  `confirm` / `confirmMessage`（二次确认）；
  声明 `settings` / `tools` / `prompts` / `skills`
  字段仍**只对 script 形态生效**（dex 的能力一律由 `activate()` 注册）。
- 安装同样**强制审批且不可永久放行**（dex 插件等价于任意代码执行）。

### 10.5 二进制兼容（宿主升级后旧插件不能崩）

清单级的 `PluginCompatibility`（10.1 / 10.3）只能看 `targetApi` 与版本范围，管不到
「插件 dex 是按旧版 API 编译的、宿主新增了接口成员」这种**类级别**的不兼容。

**编译契约**：`:plugin-api` 与 `:app` 统一用 `-Xjvm-default=all-compatibility`
（`plugin-api/build.gradle.kts` / `app/build.gradle.kts`）。接口里带默认实现的成员
（如 `Tool.readOnly`、`CommandRunner.containerWorkspacePath`）会编译成真正的 JVM
default 方法，同时保留 `DefaultImpls` 外壳 —— 旧插件类即使没有这个方法，运行期也会
落到接口默认实现，不再 `AbstractMethodError`。

**新增成员的硬约束**：
- 给 `Tool` / `CommandRunner` / `ProviderTransport` / `SystemPromptContributor` /
  `ContextStrategy` / `StorageBackend` 等插件会实现的契约**新增成员时，必须带默认实现**。
- 确需破坏性变更（新增无默认实现的抽象成员、改方法签名）时，必须同时提升
  `KairApi.VERSION`，并在发布说明中要求插件按新 `targetApi` 重编译 —— 宿主会拒绝
  `targetApi > VERSION` 的插件（前向兼容），而不是让它带病运行。
- **v8**：新增 `onAgentEvent` / `scope` / `onDeactivate` / `agents` / `dataDir`。
  全部带默认实现（空实现 / 已取消的作用域 / `null`），**旧插件不实现也语义正确**：
  不订阅就收不到事件、拿不到桥就降级、没有作用域就不跑后台任务。
- **v9**：删除 `CommandRunner.environmentNote`（**破坏性**）。通道事实已由静态系统提示的
  `container_shell` 守则覆盖；旧插件若覆盖该成员，需删掉这一处并按 `targetApi: 9` 重编译。
- **2026-10-30（不提版本）**：`CommandRunner.containerWorkspacePathFor(File)` 与
  `StorageBackend.workspaceBase()` 都是**带默认实现**的新增成员，ABI 不破，`KairApi.VERSION`
  不变；旧插件不实现时分别回退到 `containerWorkspacePath` 与「首个项目的父目录」。
- **2026-11-01（不提版本）**：`ProviderTransport.maxImagePixels(config)` 带默认实现
  （返回 `null` = 未声明端点像素上限），ABI 不破，`KairApi.VERSION` 不变；旧插件不实现时
  内核不缩放任何图片（与改造前行为一致）。LongCat 端点由内置传输层声明 `5242880`，
  缩放只发生在**图片入库前**（`core/agent/ImageDownscaler.kt`），不写进请求装配。
  同日真机追因：上限判定改为看**实际端点**（`providerId` 或 `baseUrl` 主机名），签名不变；
  内核 `ImageDownscaler.attach/store` 与 `AgentSession` 各多一个**带默认值的 `log` 参数**
  （`app` 模块内的内核接缝，不在插件 ABI 面上），因此仍不提版本。
- **2026-11-04（不提版本）**：`CommandRunner.environmentNote` 是**带默认实现**的新增成员
  （默认 `null` = 「本后端没有环境事实要说」），ABI 不破，`KairApi.VERSION` 不变；旧插件与
  本地 shell 后端不实现也语义正确。宿主侧只有内置的两条通道实现它（事实句在
  `ContainerChannelNotes`），文本按上面的确定性要求写，且**不进系统提示前缀**。
- **2026-11-21（破坏性，`KairApi.VERSION` 8 → 9，U116）**：删除 `CommandRunner.environmentNote`。
  通道事实（proot / `setsid` 也逃不出去 / 常驻走 `background_task timeout: 0`）已由静态系统
  提示里 `BashTool` 的守则覆盖，不再需要每会话追加 `[environment]` note；动态 note 机制保留，
  改为承载设置页手动探测出的 root 授权状态（`core/agent/RootNote.kt`）。旧插件若覆盖了该成员，
  需删掉这一处再重编译。
- **2026-11-11（不提版本，U47 守卫增强）**：契约默认成员的守卫从「手列成员定点核验」升级为
  **基线快照 + 反射全量比对**，只加守卫、不改契约，`KairApi.VERSION` 不变：
  - `plugin-api/src/test/resources/abi-baseline.txt` 列出全部契约接口的**可选成员**
    （带默认实现者；suspend 成员按 JVM 字节码形态记 Continuation 参数）。
    `JvmDefaultCompatibilityTest` 反射枚举 classpath 上 `dev.kair` 主源集的全部接口与其
    default 成员，与基线**双向比对**：反射有基线无（加了成员没登记）与基线有反射无
    （成员被删 / 改抽象，即 ABI 破坏）两个方向都定向红；每条基线条目再核验
    「非 abstract + `<接口>$DefaultImpls` 外壳存在」—— `all-compatibility` 的两半缺一半就红。
    新增带默认实现的成员时按测试红提示同步补基线；手列成员的旧用例全部保留。
  - `ArchitectureGuardTest` 扫描根从「app 内核」扩到 **app 内核 + `plugin-api/src/main/kotlin`**；
    引用形式覆盖 **import / 别名 import / 全限定调用** 三种（全限定写法此前能绕过检查）；
    判定先经 `KotlinSourceScanner.stripped()` 剥注释与字符串，注释示例引用不误判；
    每个源根有防空扫断言（扫不到文件即失败），并各有一个真实文件锚点证明源根真的被扫到。
- **2026-11-05（不提版本）**：给「显示文本」开资源通道 —— 应用侧 `Plugin` 新增**带默认实现**的
  `nameRes` / `descriptionRes`（默认 `null` = 逐字回退 `name` / `description` 字面量）；
  `PanelContribution` 新增**构造器参数** `titleRes: Int? = null`；`SettingsPanelSpec` 新增
  **类体属性** `var titleRes: Int? = null`。后两者形态不同，是因为 ABI 暴露面不同：
  **dex 插件自己构造 `SettingsPanelSpec`**（`ctx.settingsPanel(SettingsPanelSpec(...))`），往构造器加参数
  会改变主构造器与默认值合成构造器的 JVM 描述符，按旧版编译的插件在构造点直接 `NoSuchMethodError`；
  而 `PanelContribution` **只存在于 app 模块，第三方 SDK 的 `PluginContext` 没有 `panel()` 通道**
  （见 `KairApi.kt` 的成员清单），没有 dex 构造它，因此可以放心走构造器。
  接口成员靠 `-Xjvm-default=all-compatibility` 编译成真正的 default 方法；新增的
  `get/setTitleRes` 是**新方法**，旧插件不调用，不存在缺方法路径。三者都**不升 `KairApi.VERSION`**，
  旧插件不声明也语义正确（走字面量）；宿主解析只在 `ui/components/PluginDisplayText.kt` 一处。
  探针：`PluginTextChannelTest` 的两条 arity 用例（各自钉住「这个类的构造器形态不许再变」）
  + 一条 default 方法用例 + 一条 `copy(pluginId = …)` 是否携带 `titleRes` 的语义用例。
- **v7**：`SystemPromptContext` 新增 `workspace`（宿主真实工作区）。这是**新增字段**，
  旧插件不读它不受影响；但容器生效时 `cwd` 是容器内工作区路径（`/projects/<目录名>`），
  需要读工作区文件的提示段插件必须按 v7 重编译并改用 `workspace`，否则 `File(cwd, …)` 在
  宿主机上读不到。

**运行期巡检**：每次安装 / `discover()` 重扫后，`PluginBinaryCompat` 会扫描插件入口
与它贡献的对象（工具 / 传输层 / 提示段 / 策略 / 存储 / 命令后端），对照当前宿主契约的
**抽象成员**检查实现是否齐全：
- 缺失成员 → 插件页对应行显示红字「与当前版本不兼容：Tool.readOnly…」，用户可
  更新 / 停用 / 删除，而不是等某次工具调用才闪退。
- `activate()` 因 `AbstractMethodError` / `NoSuchMethodError` / `NoClassDefFoundError`
  等链接错误失败 → 收敛为「无法加载」条目（同样红字展示），不会把应用启动带崩。
- 脚本插件（无代码）不参与类级巡检。
