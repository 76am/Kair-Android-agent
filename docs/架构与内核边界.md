# Kair 架构

> 本文定义 Kair 的目标架构与内核边界。它是 `AGENTS.md` 第 2、3 条的展开。
> 修改内核边界、插件 API 或缓存契约时，必须同步更新本文。

---

## 1. 定位

Kair 是一个 Android 编码 Agent。设计受两条原则支配（见 `AGENTS.md`）：

1. **能力皆可插拔**：内核尽可能小，能力尽可能做成插件。
2. **高缓存命中率**：请求前缀跨回合字节稳定。

pi 不在依赖链上，仅作参考实现。

---

## 2. 目标 / 非目标

**目标**

- 新增一种模型协议、压缩策略、存储后端、UI 面板，只需新增插件，不改内核。
- 长会话下 prompt 缓存命中率尽可能高，且命中率可被观测、可回归检测。
- 面向模型的契约（工具 schema、system prompt 语义）稳定可控。

**非目标**

- 与 pi 的会话文件格式 / 内部 API 兼容。
- 一次性把 pi 的全部能力搬过来。
- 复刻 pi-web 的界面或服务端架构。

---

## 3. 分层

```
┌─────────────────────────────────────────────────────────────┐
│ UI (Compose)                                                 │
│   整屏 = 宿主提供的外壳；内容由插件贡献（面板/命令/设置分区）    │
├─────────────────────────────────────────────────────────────┤
│ 插件层 (Plugins)                                             │
│   工具 · Provider 传输层 · 上下文/压缩策略 · 系统提示构建        │
│   存储后端 · UI 贡献 · 有序中间件钩子                          │
├─────────────────────────────────────────────────────────────┤
│ 内核 (Kernel)  ← 不可插件化，见第 4 节                         │
│   消息模型 · 会话主循环 · 插件宿主(注册表+HookBus)              │
│   请求装配器（缓存稳定前缀契约）                               │
└─────────────────────────────────────────────────────────────┘
```

依赖方向**单向向下**：`ui → app → core`。`core` **不得**依赖 Android UI 或 `ui` 包。
`AppContainer` 是唯一的装配点，负责把内核与插件接到一起。U31 第一刀起，插件侧那两段搬成
协作对象：插件运行时桥（按会话的注入限流窗口 + `AgentBridge` 实现）在
`app/PluginRuntimeBridge.kt`，内置插件启用 / 禁用与动态插件删除在 `app/PluginLifecycleOps.kt`，
容器只留接线与一行委托。
core 的唯一 Android 例外是**持久化接缝**（`core/settings` 的 `Context` / `SharedPreferences`，
构造注入），逐条登记在 `ArchitectureGuardTest.allowed`（`SharedPreferences` 于批次 9 / A2 登记）。

## 4. 内核四件套（不可插件化）

| 内核块 | 职责 | 位置 |
|---|---|---|
| 消息模型 | 会话值类型（消息、内容块、用量、停止原因） | `core/model` |
| 会话主循环 | turn → 流式助手 → 执行工具 → 回灌 → 循环；会话在干什么由单一封闭状态 `TurnState`（`Idle` / `Busy` / `Running(compacting)` / `Stopping`）表达，写入口只有 `transition()`。A5 拆出三块协作件，仍在内核、不进 `plugin-api`：`HistorySanitizer`（历史修复纯函数）、`TurnQueue`（忙 / 停止期间的队列）、`TurnExecutor`（一个回合的请求装配与流式消费） | `core/agent/AgentSession`（+ `TurnState` / `HistorySanitizer` / `TurnQueue` / `TurnExecutor`） |
| 插件宿主 | 注册表（无序贡献）+ HookBus（有序钩子） | `core/plugin` |
| 请求装配器 | 把会话状态装配成「缓存稳定」的请求；每发请求的输入（模型 / 鉴权 / 工具面 / 采样 / 窗口）先解析成一份不可变快照 `ResolvedRequestInputs`，系统提示与请求 schema 共用装配产出的同一份工具列表（U42） | `core/agent` 装配路径 |

选择这四块的理由：它们是**所有插件的共同底座**。一旦插件化，就失去了稳定契约，插件之间无法协作，缓存前缀也无从保证。

会话状态机（ADR 0004）：`TurnState` 是 `core` 内部类型，**不进 `plugin-api`**（否则它就变成
改不动的 ABI）。`Busy` 是「非回合的串行动作在跑」（如删除消息），对外算忙、不算回合；
`compacting` 是 `Running` 的**相位**而不是并列状态（压缩总在某个回合内发生，拆开会让
「Running 且 Compacting」重新可表达）；`Stopping` 只能从 `Running` 进入 —— 所以
「空闲且在停止」在类型上不存在，ADR 0003 的三条结论（不同步置空闲 / 停止期间表现为忙 /
停止期间仍可发送入队）由转移表而非书写顺序保证。子智能体面板的字符串 status
（`SubagentsPlugin`）与 MCP 的 `McpServerStatus`（`core/mcp`）是另外两套概念（跨进程展示字段 /
服务器连接状态），**不在本项范围**、不随 `TurnState` 收编。

## 5. 插件能力目录

### 5.1 无序贡献（注册即用，互不影响）

| 贡献点 | 说明 | 状态 |
|---|---|---|
| 工具 `Tool` | 暴露给模型的函数 | ✅ 已有 |
| 面板 `PanelContribution` | Compose 整块 UI | ✅ 已有 |
| 操作 `ActionContribution` | 可点击动作 | ✅ 已有 |
| 命令 `CommandContribution` | 斜杠命令 `/xxx` | ✅ 已有 |
| 设置分区 `SettingsSectionContribution` | 追加到设置页 | ✅ 已有 |
| 提供方 `ProviderDef` | 出现在服务商选择器 | ✅ 已有（只引用传输层 id） |
| **Provider 传输层** `ProviderTransport` | 流式协议解析（Chat Completions / Responses / Anthropic / Gemini 原生） | ✅ 已有（内置插件 `dev.kair.plugin.transport`；未注册 id 降级为 Failure。内核在 `ProviderTransports` 之外统一包一层**瞬时失败自动重试**，传输层只需在场，见第 8 节） |
| **上下文/压缩策略** `ContextStrategy` | 何时压缩、如何摘要 | ✅ 已有（内核只认契约，内置插件 `dev.kair.plugin.context` 提供实现） |
| **系统提示构建** `SystemPromptContributor` | 有序段落贡献 | ✅ 已有（内置插件 `dev.kair.plugin.systemprompt`；内核只做按 `order` 拼接） |
| **存储后端** `StorageBackend` | 项目 / 会话 / 消息持久化实现 | ✅ 已有（内核只认契约，内置插件 `dev.kair.plugin.storage` 提供本地文件实现；无插件时回退本地文件） |
| **命令执行后端** `CommandRunner` | `bash` 工具跑命令的后端（本地 shell / proot 容器） | ✅ 已有（内核只认契约，内置插件 `dev.kair.plugin.shell` 提供 toybox 实现；无插件时回退本地 shell） |
| **文件访问后端** `FileBackend` | `read/write/edit/ls/grep/find` 的文件 I/O 后端（本地视图 / 容器视图） | ✅ 已有（内核只认契约，`ToolContext.files` 取用；默认 `LocalFileBackend`，容器在场时由宿主注入 `ContainerFileBackend`） |
| **技能** `SKILL.md` | 渐进式披露：名称+描述进系统提示索引，正文经 `skill` 工具按需加载 | ✅ 已有（内置插件 `dev.kair.plugin.skills`；技能根可由动态插件贡献，见第 10 节） |
| **动态插件** `manifest.json` + 脚本 | 运行期安装的「数据 + 脚本」插件（工具 / 提示段 / 技能） | ✅ 已有（宿主 `DynamicPluginHost`；不加载外部代码，见第 10 节） |

> `ModelCatalog` 中的提供方只引用「传输层 id + 配置」（`ProviderDef.transportId`），
> 传输层本身由插件提供；`ProviderKind` 枚举与工厂硬分支已移除。
> 存储同理：内核只认 `StorageBackend` 契约，本地文件实现（`LocalStorage`）作为一个插件注册。
> **注意**：`workspaceDir` 必须返回真实文件系统路径（工具与未来的 proot 依赖真实目录），
> 可替换的是「项目 / 会话 / 消息」的持久化介质，不是工作区本身。

### 5.2 有序钩子（可改写核心数据流）

每个钩子是一条链：处理函数接收上一环产出的值，返回替换值；返回 `null` 表示不改写。

| 钩子 | 时机 | 典型用途 |
|---|---|---|
| `input` | 用户输入变成消息之前 | 规范化、宏展开 |
| `context` | 装配请求上下文时（**瞬时，不落盘**） | 追加提醒、注入检索结果 |
| `tool_call` | 工具执行前（**挂起**） | 改写参数、拦截（block）、审批等待用户决定 |
| `tool_result` | 工具结果回灌前 | 脱敏、裁剪 |
| `before_provider_headers` | 发出 HTTP 请求前 | 追加/改写请求头 |

**约束**：钩子必须是**纯函数**（无副作用、幂等、可预测）；唯一例外是 `tool_call`
——它是挂起的，允许为等待用户审批而暂停（`ApprovalGate`，见第 8 节）。`context` 钩子**只能追加**，见第 6 节。

挂起等价于**阻塞整条工具链**，因此宿主侧有三条硬约束：

- **按会话串行、跨会话并行**：同一会话的并发请求在闸门内**排队**（每会话一把锁），不静默拒绝、
  不互相顶掉卡片；不同会话各自独立，A 的待批卡片不会被 B 遮挡。待批请求按「展示会话 id」
  索引（`Map<String, ApprovalRequest>`），面板只取当前会话那一条。
- **超时**：默认 3 分钟，且**从拿到会话锁、卡片真正展示时才开始计时**——排队时间不计入超时，
  否则排在前面的会话拖久了，后面的请求一展示就已超时。超时后该调用**不执行**，以 `blockReason`
  告诉模型「审批超时，请先询问用户是否重试」——拒绝无限挂起。
- **归属**：子智能体发起的审批带 `ownerSessionId`（沿 `parentId` 解析到顶层父会话），
  卡片显示在父会话与其详情页，而不是子会话 id 下。会话关闭时该会话的「本会话放行」规则
  一并作废（`ApprovalGate.endSession`），重开同一会话需重新授权。

## 6. 缓存架构（核心）

### 6.1 为什么重要

主流服务商对 prompt 前缀做缓存（Anthropic 显式 `cache_control` 断点、OpenAI 隐式前缀缓存）。
命中率取决于**前缀是否逐字节稳定**。一次对早期回合的改写，会让其后全部内容失效。

### 6.2 「缓存稳定前缀」契约

请求按如下顺序装配，**前缀部分必须跨回合字节稳定**：

```
┌─ 稳定前缀（可缓存，只追加）──────────────────┐
│ 1. system prompt（段落顺序固定、内容确定）      │
│ 2. 工具列表（确定顺序）                        │
│ 3. 历史回合（只追加，绝不改写）                 │
│    ↑ 缓存断点置于稳定边界（如每个完整回合之后）  │
└───────────────────────────────────────────┘
┌─ 易变尾部（不缓存）──────────────────────────┐
│ 4. 当前时间 / 临时状态 / 动态提示              │
└───────────────────────────────────────────┘
```

规则：

- **只追加**：任何对上下文的改写（含 `context` 钩子）只能追加到末尾。
  - 特例：工具集相对本会话上次记录发生变化时（改版本、装卸插件、开关工具），
    `AgentSession` 在历史**尾部追加**一条 `isSystemNote` 的 user 提示，提醒模型重读
    工具清单（模型会锚定「当时还没有该工具」的旧回合而忽略当前清单）。只追加、
    不改写，且每次变化只提示一次（基线落盘在会话级设置）。
  - 特例：每回合开始前，若历史里还没有**今天**的日期提示，`AgentSession` 在尾部追加
    一条 `isSystemNote` 的 user 回合（存盘 / wire 为英文 `2026-10-29 (Thu)`，界面经
    `dateNoteDisplayText` 显示为 `2026-10-29（周四）`，设备本地时区）。判据看「历史里
    有没有」而不是记基线 —— 提示被压缩吞掉后当天会自动补回。判重按**完整正文**匹配
    （认新 wire 与旧中文两种格式）；按日期前缀会误吞以今天日期开头的插件 note。
    同样只追加、不改写，不动系统提示前缀与 `SectionCache` 键。
  - 特例：被用户中止、且**模型输出流被掐断**的回合（`StopReason.ABORTED`），其已生成
    内容**不进请求** —— 它可能只是半句话（正文说了一半、紧随的工具调用就被掐掉），回灌会
    让模型把未完成的输出当成自己说完、做过的完整回合（例如正文说了「我这就查查」而调用
    被掐断，模型会以为自己查过了）。`AgentSession` 在装配前把该回合整条换成一条
    `(interrupted by the user)` 提示（保持 assistant 角色，避免连续两条 user）。这次改写
    只发生一次，且发生在该回合**首次进入模型可见历史之前**（被掐断的回合从未发给模型），
    因此对模型可见历史而言仍是「只追加」：此前发出去的前缀逐字节不变。界面与磁盘上的历史
    **原样保留**已生成的部分（用户要看得到被打断的半截）；只有「发给模型」那一份经过投影，
    且投影同时喂给装配前缀与实际请求，二者字节一致。
    - 判据是「模型输出流是否正常收尾」，与用户是否按停无关：流已收尾、只是**工具执行**
      被中止的回合，正文照旧发送；被中止的调用补一条
      `Tool execution was aborted by the user before it finished.` 的配对结果（已完成的
      保留真实输出），工具卡与调用都保留 —— 不再作为悬空调用被删掉。进程本身由
      `CommandRunner` 的 `killTree` 终止（**先枚举后代再终止**：Android 没有
      `ProcessHandle`，退回 `/proc` + `android.os.Process.killProcess`；chroot 的
      root 后代再经 `su` 以 root 清理）；收尾写在 `NonCancellable` 里，因为协程此时已取消。
    - 仍未产出一字就中止的回合：回收空气泡，不留任何消息与提示。
    - 中断投影（`sanitizeInterruptedTurn`）只动「流被掐断」回合里的残缺配对，且用 **CAS 提交**：
      `abort()` 不同步置空闲（ADR 0003）—— 它只把状态推到 `Stopping`，取消收尾（杀进程 /
      修配对 / 落盘）仍在跑；用户此时发下一条会入队，由收尾结束后接成新回合。按老快照整体
      赋值会把刚追加的消息吞掉，因此只在「历史仍是那份快照」时提交，否则在最新历史上重算。
- **确定性序列化**：相同逻辑状态 → 相同字节。禁止时间戳、随机 id、不稳定排序进入前缀。
- **稳定排序**：工具列表、system prompt 段落、请求头一律确定顺序。
- **易变后置**：时间等易变内容只能进「易变尾部」。
- **纯记忆化**：为省重复计算，`RequestAssembler` 记忆化工具列表的序列化结果、各
  `SystemPromptContributor` 记忆化自己那一段 —— 仅当输入未变时复用上次字节，输入
  一变即失效重算。记忆化**不改变**任何输出字节，只避免同一状态反复序列化 / 构造，
  因此不触碰上述契约。
  - 段落缓存按 `(作用域, 贡献点 id)` 分桶，每桶保留**多个上下文槽位**（默认 4，LRU）：
    主会话与子智能体（不同 `toolFilter`）、或同工作区里不同 cwd 的会话交替装配时各有各的
    槽位，不再互相覆盖而每次切换都 miss；不同工作区也不再共用那 4 格（旧布局会把最旧的
    作用域挤出去）。命中条件只覆盖「贡献点实例 / cwd / addendum / 工具列表 / 用户覆写 /
    项目 id」，
    **workspace 这一维只在桶键上**（分桶之后再进谓词就是恒真 —— 一个概念一个实现点，
    `AGENTS.md` §10.4；隔离由 `PromptCacheScopeTest.different workspaces never read the same cached section`
    单点守）。
    **存储侧是 `core/agent/PromptSectionCache.kt`**（2026-11-01 从 `SystemPrompt.kt` 搬出，
    `AGENTS.md` §10.5 的归属 / 生命周期 / 清除时机 / 并发语义四项写在它的类 KDoc）。
    **失效按作用域**（看板 **U19**，2026-11-01 第 ② 笔）：作用域取装配里**已有**的维度
    —— `SystemPromptContext.workspace`（宿主工作区路径），桶键与代数都按它走，
    所以不新增任何进入前缀的输入。`invalidate(workspaceScope)` 只摘那个工作区的桶，调用点是
    工具执行后（每回合）、压缩后、**以及删除项目时**（`AppContainer.deleteProject`，
    取路径必须在 `storage.deleteProject` 之前 —— 删完再调 `workspaceDir()` 会走 `ensureDirName`，
    它 `mkdirs()` 重建刚删的目录并把映射写回 `project-dirs.json`，正造出 `Storage.kt` 注释里
    那种「索引没有、映射还有」的占名孤儿。这一清的价值是 §10.5 的清除面（内存回收），
    **不是**正确性：`Entry` 谓词里有 `projectId`，换了项目必然 miss）；
    不带参数的 `invalidate()` 清全表，留给三类时机：改预设、注入覆写来源（改的是跨工作区
    输入）、文件编辑器保存（手上只有被存盘文件的绝对路径，推不出作用域 —— 清多了只丢一次
    命中率，清少了是旧正文一直留着）。同一工作区里的多个会话**仍**共享失效：同一个桶，
    而它们读的本就是同一份外部状态。此前一次失效打掉所有会话当回合的槽位（只丢命中率、
    不丢正确性），改法与判据见 [`维护-提示词段落缓存`](handoff/维护-提示词段落缓存.md)。
    代数也按作用域存，否则「别的会话失效 → 我的写回被当作过期丢弃」这条隐性串扰会跟着
    只清了一半（`PromptCacheScopeTest` 里 ① 与 ④ 分别钉这两半）。
    贡献点若还依赖这些之外的外部状态（如记忆插件读工作区里的 `.kair/memory.md`），该状态
    变化**不会**自动让缓存失效 —— 段落会被冻结到某项输入变化为止。需要刷新的时机：
    **工具列表变化**（已由输入条件自然覆盖）、**每个请求回合之前**（`TurnRunner.runLoop`
    在 `streamAssistant()` 前调用 `SystemPromptBuilder.invalidate(host.workspace.path)`；
    可用设置项「每回合刷新系统提示段」关闭）、**文件编辑器保存之后**（`FileEditor`，走全局那条），
    以及**压缩历史**（`CompactionRunner` 在重写历史后调用本会话作用域；此时历史段本就被重写，
    刷新不额外增加缓存损失）。**每回合刷新包含纯聊天回合** —— 后台子智能体可能在没有工具调用的
    间歇里改写记忆文件，只靠「工具执行后」刷新会让这类更新拖到压缩上下文才生效。
    代价可控的原因：重算是**纯函数重算**，外部状态未变时输出字节逐字相同，缓存前缀不受影响
    （`PromptRefreshTest` 钉住这条）。
  - **项目身份预设**：覆写来源按 `(sectionId, projectId)` 解析，且**只**覆盖开场白段
    （`dev.kair.prompt.preamble`）。交付路径不在身份段里，而是独立的锁定段
    `dev.kair.prompt.delivery`（order 2）—— 换身份不能把「用户能拿到产出」这条契约带走。
    项目绑定的预设停用或正文为空时回落到内置身份；
    未绑定预设的项目直接用内置文案 —— 没有「全局身份覆写」这条第二路径。
    项目 id 进入缓存键，因此多个项目交替装配时各用各的正文，不会互相挪用。
    绑定关系存在 `<storageRoot>/prompt-presets.json`，**不写进 `Project`** —— 给
    `plugin-api` 的数据类加字段会改 JVM 构造签名，旧插件会 `NoSuchMethodError`。
  - **失效与计算并发**：`invalidate()` 先递增缓存代数再清空；贡献点计算期间被失效的，
    写回时发现代数已变就丢弃结果，避免「算得慢的会话把失效前状态算出的正文重新冻结」。
  - **异常隔离（按「内置 vs 外部」分流）**：**外部**贡献点（插件 / 读盘技能）抛异常只让
    该段缺席（按 null 处理并清掉对应槽位），不允许冒泡拖垮整段系统提示装配 —— 否则该会话
    之后每一回合都会变成 `Error`。判据是**实例引用**（`BuiltinPromptSections.isBuiltin`），
    不是 id —— 插件撞名不会获得「抛了也不隔离」的待遇。
    **内置**段落**不隔离**：它们抛异常是内核 bug，必须让当回合响亮地失败，而不是把「整段
    提示悄悄少了一节」变成一个更难查的静默缺陷。
  - **隔离与可见成对出现**：缺席 / 异常按 `(id, 成因)` 记进 `Diagnostics.sectionIssues`
    （按会话、覆盖式，随会话关闭清理），面板只读展示。判据是「注册了就应当有产出」——
    遍历传入的**全部**贡献点，正文为空即记一条缺席，因此「漏注册 / 注册了却永远返回空」
    在装配结果里可见。只兜底不报告，等于把「整段失败」换成「整段悄悄没了」，更难查。
  - **null 不缓存**：贡献点返回 null（读失败 / 暂时缺席）时不登记缓存，下次请求重算。
    否则一次瞬时失败（典型：记忆文件被容器以 root 创建，应用进程读不到而抛异常）会被
    冻结成永久缺席，同工作区的新会话也会命中同一条缓存。外部状态的刷新仍只靠上面列出的
    时机，不额外引入「每回合重算」的旁路。
  - 清缓存不改变输出字节：贡献点内容未变时重算结果逐字一致，因此不破坏缓存稳定前缀，
    只是多一次本地字符串构造。

### 6.3 命中率检查面板

一个由插件贡献的面板，展示最近一次请求：

- 各前缀段的大小与内容摘要；
- 与上一回合相比**哪些段发生了变化**（前缀是否被破坏）；
- **命中率读数两个**（原为三个，2026-11-04 负责人砍掉「最近命中率」那一行：既刺眼又最容易被当结论读。
  被砍的那个口径记在下面第 3 条，留档是为了让「面板为什么只剩两个数」有出处）：
  1. 「本会话累计」= 按 **token 加权**的 `sum(cacheRead) / sum(prompt)`
     （`CacheReport.hitTally`）—— 回答「这个会话一共省了多少」，**面板上那个命中率就是它**。
     不取逐发比值的平均：
     平均会被少量输入的请求带偏（一发 100 token 的 10% 与一发 5 万 token 的 90%
     在平均里各占一半，在真实花费里根本不是）；提供商没回缓存字段的**那些发**逐个计数显形
     （`unratedRequests`；单位是「发」= 一次 usage 事件，一个回合最多 `maxSteps` 发 —— 字段原名带
     `Turns` 是这个单位说反了，第三轮 B 审 P2 已改名），否则趋势图少点而面板不说，
     用户会把「少点」读成「历史只有这么短」；
  2. 「段落缓存」= **本地** `PromptSectionCache` 在**产生这一发请求的那次装配**里复用了几段正文，
     未命中再分「无缓存可复用」与「输入已变」两类（`CacheReport.sectionCache`，见本节末段）。
     它省的是**重算**（读工作区文件、拼正文），**一个 token 都不省** —— 与第 1 条不是同一件事。
  3. 【已撤】「最近命中率」= 从 `usage` 观测到的**单发**比值 `cacheRead / (input + cacheRead + cacheWrite)`。
     它天生在两端跳（重写前缀那一发低、下一发几乎全命中），当结论读就是误读，所以面板不再为它
     单列一行，`CacheReport.cacheHitRate` 字段随之删除 —— 单发比值只存在 `CacheReport.samples` 里，
     作为趋势折线的**点**出现。对话页底部的上下文圆环也读同一份 `CacheReport.hitTally.weightedRate`
     （2026-11-07 统一口径，不再走 `Usage.cacheHitRate` 那条逐发路径），两处显示的是同一个数。
- 最近若干次命中率的**趋势折线**，样本**按会话各留 60 条**（`CacheReport.samples`，
  上限 = `CacheInspector.historyLimit`）—— 单看最近一次无法判断缓存是在变好还是变坏。
  此前是「全进程共用一条 `takeLast(60)`，面板再按当前会话筛」：并发会话会把本会话的点挤出去，
  显示出来的就是「最近两发的历史」。样本现在**存在该会话自己那份报告里**，不另立并行表 ——
  并行表要有第二份回收义务，且「会话已关闭、usage 才迟到」会把那条目悄悄重建；
  于是 `CacheInspector.remove` 摘掉报告就等于摘掉累计与样本，回收路径与改动前同一条。

目的：把「缓存命中率」从直觉变成**可观测、可回归**的指标。

**口径提醒：面板里的「前缀大小」是字节，对话页底部的上下文圆环是 token。** 两者本就不同
（同一段中文约 3 字节 / token），界面必须带单位（`KB` / `MB`），否则容易把「800 KB 前缀」
误读成「800k token」。模型商计上下文与计费用的是 **token**（`input + cacheRead + cacheWrite`）。

> 2026-11-04 第四轮之后这一对照**只剩单位本身**：面板顶部那行「稳定前缀 X · 合计 Y」与
> 「提供商实测 N token（缓存命中 M），与底部上下文圆环同口径」一起删了，模型名与
> 「前缀只追加，缓存安全」总判定也删了。字节数现在只出现在**每个分段卡片的右侧**；
> 提供商侧的 token 总量看对话页底部圆环，缓存面板不再在同一屏里说两遍。
> 「前缀被改写过」这个信号没丢 —— 分段列表的变化列会写「改写」并标红，还直接指出是哪一段。
> 展示字段 `CacheReport.prefixIntact` / `prefixBytes` / `totalBytes` / `promptTokens` /
> `cachedTokens` 随之删除；加权的分子分母存在 `HitRateTally.promptTokensSum` /
> `cachedTokensSum`，`AssemblyResult.prefixBytes` / `totalBytes` 仍在（装配侧的口径，另一件事）。

**段落缓存的读数与归因（U30，2026-11-02）**。U19 第 ② 笔把失效改成按作用域，但当时**没有**
任何面能证明它生效 —— `PromptSectionCache.find` 的命中信息在装配层就地丢掉（返回 `String?`，
null 就是 miss，为什么 miss 无人知道）。现在 `find` 返回 `SectionLookup(section, miss)`，
归因三类：命中 / `NOTHING_TO_REUSE`（该作用域下压根没有这个贡献点的槽位）/ `INPUT_CHANGED`
（槽位在、但没有一条输入相等）。一次装配把三类计数累成 `SectionCacheStats`，随
`PromptAssembly.sectionCache` → `AgentAssembly.sectionCache` 一路交给**发出这一发请求的**
`TurnExecutor`，由它调 `CacheInspector.record(..., sectionCache)` 记进那一发的报告 ——
**它是装配的局部结果，不是新的常驻计数器**，所以 §10.5 那四项在装配层没有要答的题。

**为什么不让宿主「顺手记一份」**（第一轮 B 审 P1）：一个回合里 `agentSettings` 会被调**好几次**
（`TurnRunner.kt:213` 取 maxSteps、`:235` 取 model、`CompactionRunner.kt:83/89` 估 token、
`AgentSession.contextWindow()` 给界面取窗口），请求**之后**那一次几乎必然全命中。观测器若只存
「最近记到的那份」，那一发请求的报告就会被改写成与它实际相反的数。读数因此只能跟着**它自己那次
装配的产物**走；宿主侧那条路已由 `SectionCacheStatsTest` **反向**钉住（容器里不得再出现
`recordSectionCache`）。常驻的那一份仍是 `CacheInspector` 里按会话的报告（随 `remove` 回收，
与诊断同一时机；子智能体用临时实例，因为它不进 `SessionRegistry`，没有谁调它的 `remove`）。

**归因只有两类是刻意的**：`NOTHING_TO_REUSE` 同时涵盖「本进程第一次为这个工作区装配」与
「刚被 `clear` 摘走」—— 两者在存储侧看不出区别（桶都不存在），要分开就得再养一份
「见过但没有」的登记表（多一个对外出口 + 多一条生命周期），而冷启动每个工作区每进程
只发生一次，污染不了趋势形状。取舍与判据写在 `PromptSectionCache` 的 KDoc 与
[`维护-命中率观测面`](handoff/维护-命中率观测面.md) §3.1。

这条读数同时是 **U19 ② 的回归探针**：用例
`SectionCacheStatsTest.another workspace invalidation costs this workspace no hits`
断言「预热 A / B 两个作用域后失效 B，A 当回合仍必须全命中」—— 退回全表清它必红。

分段详情提供两个视图：**可读**（给人看的渲染，会加「💭 思考」等标签）与**原始前缀**
（用于计量缓存前缀的规范化投影，`\0` / `\1` / `\2` 分隔符转义为可见形式）。后者不是 HTTP 报文
本身，分隔符也不会发给模型；它用来核对 Kair 的字节口径到底算了哪些内容。

**展示口径**：四段的 canonical 都整段按会话长期持有，所以详情页要不要截尾只按「规模」判：
**只有历史段随回合数与消息体量线性增长**（长会话可达数百 KB，是唯一能把 Compose 排版顶崩的量级），
它只留尾部 `DISPLAY_LIMIT`；系统提示 / 工具列表 / 请求尾部的上界由「配置 + 各贡献点自己的产出」决定
（段落数、工具数、参数量；系统提示里也有读工作区文件的段落，例如记忆插件读 `.kair/memory.md`，
那份文件多长它就多长），截它们只会让人看不清「这段到底塞了什么」，所以整段给出。
判据与「不截尾」的写法集中在 `SegmentKind.displayBudget` 一处，面板与观测器不再各写一份
`kind == HISTORY`。**放开的是展示截断，不是内存保证**：有界段多物化一份的上界 ≤ 它自己的 canonical。

**内存约束**：分段快照会长期按会话保留，因此可读文本一律**按需生成**（`RequestSegment.readable`
只在面板点开时物化）。「本次新增」在装配时就算好并截断（`CacheReport.appended`），面板不再保存
上一回合全文、也不在点击时对整段历史做 `startsWith` / `removePrefix` 复制 —— 长会话下那一步会把
主线程顶到 OOM。

已实现：内核 `core/agent/RequestAssembler` 在装配时显式切出四段
（系统提示 / 工具列表 / 历史回合 / 请求尾部），`core/agent/CacheInspector`
记录分段快照与命中率样本并与同会话上一回合比对；内置插件 `dev.kair.plugin.cache`
贡献 `panels.cache` 面板展示这些数据（含命中率折线），对话页底部「缓存」按钮可直达。

同一块面板还承载**失败可见**（`Diagnostics`），分区**置顶** —— 没有请求记录时也要能看见
「哪一段没进提示」：

| 事件 | 归属 | 来源 |
|---|---|---|
| 段落缺席 / 贡献点异常（含 id 与异常类型） | 会话 | `Diagnostics.sectionIssues`（§6.2） |
| 压缩降级（摘要失败 → 机械检查点） | 会话 | `Diagnostics.compactionFailures` |
| 插件装载失败 | 应用 | `DynamicPluginHost.loadFailures`（§10.5，**复用**） |
| 技能文件被跳过 | 应用 | `SkillRegistry.loadFailures`（§10.1） |
| 插件投递失败（永久 / 临时分类计数） | 应用 | `Diagnostics.deliveryFailures` |
| 功能就地提示（记忆插件：过期隐藏 / 预算截断 / 读失败） | 功能自持键（记忆插件按工作区） | `Diagnostics.notices` |

命中率折线与诊断**同屏**：命中率断崖往往就是段落缺席的第一个信号。
按会话的记录随会话关闭清理（与 `CacheInspector.remove` 同一处、同一时机）；
应用级的两个是**定长**计数器 / 整表替换，不随回合增长；`notices` 的键空间与清理归记录它的
功能自己（记忆插件在卸载时清 `memory:` 前缀，容量受工作区数约束）。
诊断是**只读旁路**：不参与请求装配，读它不会改变任何一位请求字节。

`CacheInspector.latest` **按会话 id 索引**（`Map<String, CacheReport>`），面板按当前会话
（`AppContainer.activeSessionId`）取用 —— 多会话并发时，若按「最后一次装配」取就会显示
别的会话的数据。命中率趋势样本**也按会话分池**（`CacheReport.samples`，每会话各留
`historyLimit` 条，U30 之前是一条进程共用的 `takeLast(60)` 再让面板按会话筛 —— 那会把
本会话的历史挤光）。
每份报告都持有整段 `segments` 快照，因此 `releaseSession` 会调用 `CacheInspector.remove(id)`
回收（会话页进入时 `getOrPut`、离开时不关闭，不回收会随「访问过的会话数 × 历史长度」增长）。
同理 `AppContainer.openSessions` 有上限（默认 8）并按最近打开时间淘汰**空闲**实例：
运行中的会话（`TurnState` 非 `Idle`：回合 / 压缩 / 只改历史的串行动作）与有排队消息的会话、
以及当前会话一律不卸载（可从存储重新载入）。

**后台注入不改变「当前项目 / 当前会话」**：`AgentBridge.send` 给未打开的会话投消息时走
`sessionFor`（只建实例），不走 `openSession`（那会切 `activeWorkspace` / `activeSessionId`、
重连 stdio MCP）。否则定时任务给另一个项目的会话发一条，用户正在看的工作区与缓存面板
会在后台被悄悄切走。宿主尚没有活动会话（`activeSessionId == null`）时才沿用正常路径，
让容器 / MCP 能按目标工作区首次启动。

### 6.4 图片不进日志：内容寻址附件

图片 base64 本体是长会话下**日志膨胀、坏数据、端点拒答**的共同来源。因此**本体不写入
会话日志**：日志里的图片部件只保留一条**内容寻址引用** `Part.Image.ref`
（`AttachmentRef(sha256, mediaType, width, height)`），本体按 sha256 落在附件存储
（工作区 `.kair/attachments/v1`，两位分桶，临时文件 + 原子改名写入）。

- **落盘在 append 时**（`AgentSession.append → ImageDownscaler.attach → store`）：任何来源的内联图片
  （用户附加、`read_image` 回带）在进入历史前统一落地为引用，日志从此不含本体；落地失败（坏 base64 /
  磁盘错误）退回内联 base64，不阻断发送。
- **落盘前先按端点上限缩放**（U23）：上限是**端点能力**（`ProviderTransport.maxImagePixels`，按真正
  在调的那个端点判定 —— `providerId` 或 `baseUrl` 主机名，只认目录条目会让「自定义条目指向同一端点」
  拿到不同上限）。位图解码在装配层（`app/app/BitmapImageScaler.kt`），`core` 不引 Android 图形类型；
  缩放只改**入库前**的字节，请求装配期不回写历史，缓存前缀不受影响。**每条决策落一行**
  （logcat tag `KairImage`，内核 `store` 一行 + 位图一行）：四条降级落点（无上限 / 读上限抛 /
  缩放器返回 null / 缩放器抛）在设备上原本都表现为「原样发出去」，没有这行日志就只能靠猜。
- **水合在请求装配时**（`TurnExecutor.hydrateAttachments`）：只对装配出的**请求副本**按引用
  读回 base64，内存与日志始终保持无本体的引用形态；读不到本体时保留引用，由传输层跳过该图，
  不阻断本次请求。
- **缓存安全**：内容寻址 → 同一字节永远得到同一 sha，水合出的 base64 逐字节稳定；
  `RequestAssembler` 的前缀摘要直接用 `ref.sha256`，与「是否已水合」无关，前缀跨回合字节稳定。
- **向前兼容**：旧会话内联 base64（`ref == null`）原样可读；只有 `ref != null` 才触发水合，
  两种形态在历史里并存、互不影响。
- **token 估算**：已知像素尺寸时按视觉编码器口径 `⌈w/28⌉×⌈h/28⌉`（与 Claude 一致）计入，
  否则退回固定估值 1500，取两者较大值 —— 只高估不低估（见 `Compaction.imageTokens`）。
- **UI 渲染**：`ImagePart` 同时支持内联 base64 与附件读回（缓存 key 优先用 sha256），
  由会话把 `attachmentStore` 透传进消息列表。
- **回收（sweep）**：本体库是**只增不减**的 —— 去重保证「同字节一份」，但被压缩 / 编辑撤回 /
  删除消息 / 删除会话挤掉的历史图片会变成**无引用残留**。由宿主在维护时机调用 `AttachmentStore.sweep`，
  删掉所有 sha 不在引用集合里的文件并清空分桶目录；引用集合取「该项目全部会话日志 ∪ 全部在场
  会话内存历史」的**并集**（宁可多留，**绝不**删仍被引用的本体 —— 那会让水合字节改变、破坏
  缓存前缀），且**跳过新近写入（默认 2 分钟）**的文件以兜底并发写窗口。触发点：历史改写
  （压缩 / 图片降级 / 编辑撤回 / 删除消息）后去抖调度、删除会话后立即回收，以及 `/gc` 维护命令。
  **不做** LRU / 容量淘汰：淘汰仍被引用的图就等于破坏缓存契约。

**删除语义（项目 / 会话 / 文件管理器三处一致）**：删除项目必须**级联**删除它名下的会话索引项
与 `<id>.jsonl` 日志，再回收附件；只删项目会让 UI 里项目消失、而文件永久残留在 `sessions/` 下。
工作区文件面板允许删除会话日志，但必须走 `AppContainer.deleteSessionLog`（关会话 → 删索引 →
回收附件）联动收尾；索引文件 `sessions.json` 与会话目录本身仍受保护，日志也不允许改名 / 移动。

## 7. 数据流

```
用户输入
  → [hook: input]
  → 会话主循环
      → 请求装配器（先把被掐断的回合换成中断提示（见 6.2）、引用式图片水合回 base64
         （见 6.4），都只作用于请求副本）
          → system prompt 贡献点（有序）
          → 工具列表（稳定排序）
          → 历史回合（只追加）+ [hook: context]（仅末尾追加）
          → 易变尾部
      → [hook: before_provider_headers]
      → Provider 传输层插件（流式解析）
      → 助手回合
      → 对每个工具调用：
          → [hook: tool_call]（可改写/拦截；审批闸门可挂起等待用户决定）
          → 工具执行
          → [hook: tool_result]（可改写）
          → 回灌
      → 上下文/压缩策略插件（按需压缩，产生检查点；U58 起模型也可经 `compact_context`
        工具主动请求 —— 工具只置位，下一步开头才真正压缩，避免拆散 tool_call / 结果配对）
  → 持久化（存储后端插件）
```

- **历史写入只有一个受控入口**（U43）：`AgentSession` 的 `HistoryWriter` 把「会话是否已作废」的
  判断与提交收进同一把锁。回合执行器拿到的不是原始 `onPersist`，而是 `writer.append` 的受控闭包，
  因此取消收尾 / 正常收尾都绕不开这道闸。`discard()` 与提交共用这把锁，返回后不再有新的持久化
  提交开始；取消收尾仍会跑完，但它写的历史不再落盘。它**不等待**取消 `join`（调用方可能在主线程）。
  淘汰（`evict`）不走这条闸门 —— 淘汰不清会话级状态，只有 `discard()` 才作废写入。
  唯一例外是**载入期**的 `loadHistory(...)`：它仍直接调 `onReplaceHistory`（只在会话刚创建、
  还没有作废语义时调用，见 `SessionLifecycle`），不在本闸门内。
- **写入面另有一道「轮次归属」闸**（U77，`core/agent/HistoryWrites.kt`）：内存副本与落盘成对，
  五条通路分两类 —— 新增 / 覆盖 / **整份重写**属于被强制放弃的那一轮时一律丢弃；**配对修复**
  始终放行（ADR 0003 要求取消收尾把悬空 `tool_call` 补齐，挡了就是「历史干净了但请求发不出去」）。
  归属 = 当前持有串行闸门的那个任务，不用会话级布尔量：布尔量会把下一轮的合法写入一起挡掉，
  也回答不了「被放弃那一轮的压缩提交算不算数」。

### 7.1 模型解析（单一入口）

一个会话到底用哪个模型，**只在 `ModelResolution` 一处解析**，其余四处只接受结果：

| 用途 | 方法 |
|---|---|
| 系统提示里的模型名 + 采样参数 | `agentSettings(model, …)` |
| 鉴权与端点（baseUrl / apiKey / 协议） | `providerConfigFor(model)` |
| 视觉工具可见性（`read_image` 是否进 schema） | `toolEnabled(model)` |
| 上下文窗口 / 压缩线 | `resolveContextWindow(model, fallbackName)` |
| 压缩摘要的模型 / 端点（「压缩模型」设置，空 = 会话模型） | `ModelResolution.resolveCompaction(saved, compactionId, sessionModel)` |
| 子智能体会话 | `createSubAgentSession(…, modelId)` → `subagentModel(ownerId, modelId)` |

以上**解析本体**（`agentSettings` / `providerConfigFor` / `toolEnabled` /
`resolveContextWindow` / `subagentModel`）都在 `app/app/SessionAssembly.kt`（U31 ③-a 搬出），
`AppContainer` 只留同名委托；第五行里只剩 `createSubAgentSession` 的**编排**仍归容器（③-b 再搬）。
「压缩模型」的覆盖解析在 `core/settings/ModelResolution.resolveCompaction`，由 `SessionAssembly`
随主请求装进 `ResolvedRequestInputs.compactionTarget`（U113；只换写摘要的模型，不换压缩线与窗口）。

覆盖优先级（高 → 低）：**本次运行**（`subagent` 工具的 `model` 参数、插件的 `runSubagent`）
> **子智能体默认**（设置项）> **会话级**（输入框底部切换器）> **全局默认** > 列表第一条。
任一层指向已删除的模型时静默落到下一层（否则子智能体一启动就失败，而用户看不出原因）。

为什么不能各处自己解一次：只要某一处多了一层覆盖，就会出现「提示用 A 模型、鉴权走 B、
窗口按 C、视觉工具按 D」的错位 —— 接错端点 401/404、窗口算错提前压缩或撞窗、
视觉工具错位让模型调用它用不了的工具（`AGENTS.md` §10.4）。

### 7.2 回合终止原因（U48）

一个回合怎么结束，**必须可枚举、可持久化、可展示**：`TurnRunner.runLoop` 显式携带本轮
终止原因，回合壳把它广播进 `AgentEvent.TurnEnd.stopReason`（`plugin-api`）——
**不许反查历史**：空回合被丢弃后历史里没有它的痕迹，反查只能读到上一回合的旧原因。
`stopReason` 不得为 null 或含义不明的 STOP。

| 值 | 含义 | 产生点 |
|---|---|---|
| `stop` / `toolUse` | 模型正常收尾（说完了 / 以工具调用收尾） | 回合自带 stopReason |
| `length` | 输出被长度截断（截断的调用配对补齐） | `runLoop` 的 LENGTH 出口 |
| `error` | 本轮出错（错误气泡 + 中断收尾） | 回合壳异常分支 |
| `aborted` | 用户点停止 | 取消收尾（closed = false） |
| `stepLimit` | 本回合步数用尽（maxSteps 到点） | `runLoop` 步数出口；回合真正终止于上限时追加一条 `isSystemNote` 中文提示（只追加到历史尾部、**不进缓存前缀**） |
| `emptyResponse` | 模型只回结束原因，无正文无工具（不落盘、不建气泡） | `TurnExecutor` 空回合出口；`Diagnostics` 按会话计数（历史无痕，诊断是唯一痕迹） |
| `sessionClosed` | 会话关闭 / 被淘汰（区别于用户中止） | 取消收尾（closed = true） |

常量在 `plugin-api` 的 `StopReason`，**只增不改**（旧值是持久化字段，改值会让历史日志断代）；
界面（消息气泡底栏）按 `strings.xml` 映射成中文，未知值原样显示，旧日志读回不崩。
中止的收尾行为（`sanitizeInterrupted`、消息级 `ABORTED`、中断提示）不随终止原因区分而变。

## 8. 实现状态与路线图

**已落地**

- 内核：消息模型、会话主循环、插件宿主、HookBus。
- 无序贡献：工具 / 面板 / 操作 / 命令 / 设置分区 / 提供方注册。
- 有序钩子：五个钩子全部接入主循环与请求装配。
- 缓存：历史只追加（`replaceHistory` 仅用于压缩/编辑这类显式操作）、`context` 钩子不落盘。中断收尾、开/重启会话与**每次请求装配前**都会走一次 `HistorySanitizer.repairHistory`（A5 拆出的纯函数集合，`List → List`、无状态），它做三件事：① **工具调用配对修复**（`repairToolPairing`）：丢掉没有对应 `tool_result` 的 `tool_call` 与无主的 `tool_result` —— 悬空的调用会让之后每一回合的请求被 provider 拒绝（长会话下被服务端直接关流 / 报空响应）；② **非法工具参数规范化**（`repairToolArguments`）：模型偶尔吐出不是**严格**合法 JSON 对象的 `arguments`（未转义引号 / 被输出上限截断 / 未加引号的占位符如 `<longcat_arg_value>`），原样回传会让端点解析失败并吞掉整轮请求（U61 真机：HTTP 200 + 空流，重试重发同一份字节必然同样失败），历史与界面保留模型原文，**发出去的那份**统一收敛成 `{}`。判据唯一落点 `parseToolArguments`（U61，plugin-api 顶层函数，工具执行 / 历史修复 / 钩子链三处共用）：**宽松解析成功不等于端点接受**（kotlinx 1.4.1 即使 `isLenient = false` 也接受未加引号的值），故自走严格语法游标，并设 **128 层嵌套上限**挡病态输入 —— 递归下降无上限会抛 `StackOverflowError`，它是 Error 不是 Exception、三处都不接，脏历史已持久化时该会话每次装配都会炸；③ **用户控制字符剥离**（`sanitizeUserText`）：用户从缓存面板 / 终端复制回来的 `\u0000` / `\u0001` 等分隔符不可读且会永久回灌给模型，在历史与输入入口一并剔除（assistant 正文可能带厂商签名，不改写）。三项修复都是幂等的：历史本就干净时逐字节不变，只有真正有问题的回合才被改写。
- 缓存契约：`RequestAssembler` 显式分段（系统提示 / 工具列表 / 历史回合 / 请求尾部）并对每段做确定性摘要；`CacheInspector` 记录快照、判定前缀是否只追加；内置缓存与诊断面板（`dev.kair.plugin.cache` → `panels.cache`）展示分段差异、命中率，以及**失败可见**的只读诊断（段落缺席 / 压缩降级 / 装载失败 / 技能跳过 / 投递失败，见 §6.3）。
- 注入提示的 wire 语义（2026-10-31）：`isSystemNote` 的 user 消息在 `RequestAssembler` 装配时统一包 `<system-note>…</system-note>` —— 角色仍是 user（中途 system 跨 provider 不可移植），但模型能识别来源；存盘文本与 UI 卡片不变，`canonicalMessages` / `readableMessages` 用同一份包好的文本，缓存口径等于实际发送字节。压缩摘要的 `serializeConversation` 把这类消息标成 `[System note]`，不再当作 `[User]`。日期提示的 wire 文案为英文 `2026-10-31 (Sat)`，界面经 `dateNoteDisplayText` 本地化为中文；旧中文格式的 note 不迁移，判重按**完整正文**（新 wire 与旧中文两种格式），不用日期前缀（会误吞以今天日期开头的插件 note）。**上线后所有会话会因系统提示新增一行 rules 首次 cache miss；含注入提示的会话另有旧 note 序列化字节变化的一次 miss**，之后稳定。
- 上下文/压缩策略插件化：内核只认 `ContextStrategy` 契约（`shouldCompact` / `plan(messages, settings, trigger)` / `summarize` / `wrapSummary`），实现由内置插件 `dev.kair.plugin.context` 提供（`SummarizingContextStrategy`）；无插件时内核降级为不压缩。`plan` 的 `trigger` 区分常规压力（`PRESSURE`）与上下文溢出（`CONTEXT_OVERFLOW` —— 端点已拒答、且内核独立确认仍超预算）；用户点「压缩」也走 `PRESSURE`（手动入口 `compactNow` 直接调 `run`，不经过 `shouldCompact` 的预算判定，不需要任何豁免标志）。**判定进入压缩就压到底 —— 没有「降级后已回到预算内就不压缩」的短路**（2026-10-31 定），`overBudget` 只用来判断「溢出信号可不可信」；仅 `CONTEXT_OVERFLOW` 在常规计划为空时才允许 `Compaction.forcedPlan` 的有损兜底（丢最旧整轮对话）；正常压力压缩不丢数据。用量估算（`Compaction.estimateContextTokens`）**信任最新一条 assistant 的 usage**（对整段上下文的实测），只对 usage 之后新增的消息用 `chars/4` 兜底 —— 不再「只要历史里出现过压缩检查点就整体回退启发式」（那会把检查点之后累积的大量有效 usage 一起丢掉、长期低估）。估算口径与真实请求对齐：thinking 与签名按装配投影计入（「回传思考内容」开关关闭时不回灌、也不计入）；`ABORTED` 回合按装配投影后的中断提示估算；`compactIfNeeded` 另加 system prompt 与工具 schema 的固定前缀。压缩会重写前缀、让被保留消息上的旧 usage 失真，故压缩时用 `Compaction.dropStaleUsage` 把失真 usage 清掉（usage 不进请求字节，清掉不影响缓存前缀），避免「压缩后仍显示压缩前大值」并反复触发压缩。图片部件按其像素口径（`⌈w/28⌉×⌈h/28⌉`）/ 固定估值 1500 单独计入，不再像旧实现那样当 0（见第 6.4 节）。摘要请求与主请求共用 `retryingStream` 重试与 `before_provider_headers` 注入的请求头。**摘要失败不再静默回滚**：历史停在原地 = 上下文仍超窗 → 下一回合再次溢出、再次失败，会话永久卡在这条路径上。因此摘要做不出来时退化为**机械检查点**（`Compaction.MECHANICAL_CHECKPOINT`，不调模型、正文是常量、按策略已算好的切点硬切）—— 有损，但换回一条能继续走下去的历史；失败本身进诊断（`Diagnostics.compactionFailures`，按会话、覆盖式，摘要成功后清除），重写历史本身失败（落盘 I/O 等）同样记诊断。
- 瞬时失败自动重试（`TransientRetry`）：内核在传输层之上统一包一层，**所有**传输层（含第三方插件）共享同一套判定、退避与上限。两条硬约束对齐 Claude Code / Codex 的既有行为：① **只在本次尝试尚未产出任何可见输出时**重发 —— 已有 token 流出就不再重发，避免重复输出 / 重复计费 / 内容错位，宁可把失败报给用户（由他决定是否撤回重发）；② **只重发能确定是瞬时的失败**（HTTP 408/409/429/≥500、过载 / 限流 / 容量 / 超时、空响应，或传输层显式标注 `StreamEvent.Failure.retryable`），鉴权 / 参数 / 配额类重试无意义。错误体先经 `ErrorParser` 递归解析（兼容 OpenAI / Anthropic / Google / 中转站裸 `message`）再结合状态码分类，因此 `HTTP 429: insufficient_quota` 不会被误判成可重试。**分类只服务重试判定，不进入转录**：展示给用户的是 HTTP 状态码 + 服务端原文（`describeError`，最多 500 字符，超出标注「已截断」并指向「请求诊断」导出；正常 API 错误只有几百字符，上限只防网关返回整页 HTML 撑爆上下文）。原因是归类必然在边界上猜错 —— 402 余额不足曾被译成「请求参数有误」—— 原文才是唯一能回答「到底哪里错了」的东西。本地异常（没有拿到 HTTP 响应）在源头由 `localFailureMessage` **按异常类型**换成中文（请求超时 / 域名解析失败 / TLS 握手失败 / 连接被拒绝 / 连接被中断；非 `IOException` 的意外异常归「内部错误」，不伪装成网络问题），原文放进括号供排查 —— 不翻译服务端原文，也不匹配英文关键字（`getMessage()` 在厂商 ROM 上文案不同）；导出文件里的异常摘要保持英文原文，那是诊断通道。退避 1s → 2s（封顶 8s）、尊重服务端 `Retry-After`（封顶 30s）、单回合最多 3 次尝试。链路空闲超时（看门狗）**不**重试：它无法区分「链路卡住」与「模型长时间思考」，重试只会把「慢」放大成「每次再等 120 秒」（Codex 的反面教训）。
- 流式段落生命周期：传输层可上报 `TextStart/TextEnd`、`ReasoningStart/ReasoningEnd`（`id` 为稳定 part id），`TurnExecutor` 据此维护**有序段落**，「推理 → 正文 → 工具 → 正文」不再被压平成「全部推理 + 全部正文 + 工具」；只发旧 `TextDelta/ReasoningDelta` 的传输层仍按当前打开段落追加，契约向后兼容。`TextEnd` / `ToolCallStarted` / `ReasoningEnd` 另带可选的 `signature`（Gemini `thoughtSignature`、Anthropic `signature` / `redacted_thinking.data`、OpenAI 兼容的思考字段名、Responses 的 reasoning item），内核记入 `Part.Text` / `Part.ToolCall` / `Part.Thinking` 并在下次请求中原样回灌；该字段只对**同一来源端点**有效：来源键是 `(providerId, providerHost, model)` 三元组（`providerHost` 是 `hostOf()` 归一化后的主机名，不是完整 baseUrl），判据唯一落点是 `plugin-api/…/core/ai/ThinkingReplay.kt` 的 `replaysThinkingTo`，前缀摘要两处与四个传输层共六处都调它；任一侧字段缺失（老会话没有来源）一律按 foreign 不回传，不猜地址、不按模型名反推厂商（U76）。思考回传受模型配置「回传思考内容」开关控制（默认开启）：关闭时历史投影剔除全部 `Part.Thinking`，`Part.Thinking` 只在界面与日志中保留。「缺 `reasoning_content` 会 400」是**端点属性**，按 `OpenAiProvider.kt` 的 `EchoRequired` 显式表判定（host 精确匹配 → 需要补空串的 model 集合，空集 = 该 host 全部），**默认不补**：2026-11-12 实测 `deepseek-flash` 与 `LongCat-2.5` 带 `tools` 且完全不给该字段都是 200，表里只留老模型 `deepseek-chat` / `deepseek-reasoner` 的位置（U76；原先的 `contains("deepseek")` 子串判定已删除）。最终错误展示为 HTTP 状态码 + 服务端原文，不做中文归类翻译（见上条）。
- 请求捕获与导出（`RequestCapture`）：会话文件只存消息、不含请求体，排查「端点为什么拒收」必须看线上那一份。捕获点放在共用 `HttpClient` 的拦截器上（一个概念一个实现点，新增传输层自动获得该能力），传输层用 `CaptureTag(sessionId)` 标记，模型探测等非 Agent 请求不抓。成功响应**不读 body**（会打断 SSE），只有非 2xx 才 `peekBody` 取错误原文，上限 8KB（多取 1 字节判断是否超限，超出时导出 `meta.responseTruncated = true`）。缓冲按会话隔离、保留**最近 2 条请求 + 更早的至多 3 条失败请求**、单条上限 2MB（超限先脱敏图片再截断并标注 `truncated`），**只在内存**、不落盘（避免把带历史正文的请求长期留在磁盘）；请求体超过 1MB 时**跳过**捕获（序列化那一瞬间的整份 String 会再占一份内存），只留端点 / 状态 / 体积并标 `bodySkipped`。入库时对 URL 的 query 做脱敏，但**只抹名字像凭据的参数**（`key` / `api_key` / `token` / `sig` / `signature` / `secret` / `password` / `auth` 等，大小写不敏感），`alt=sse` 这类诊断参数原样保留 —— 全抹会让「端点为什么拒收」无法排查；删除会话时 `RequestCapture.clear`。「2 + 3」的理由：请求是累积快照，第 N 条包含前面全部回合，总量随回合数平方增长；成功请求的旧副本没有复用价值（下一次请求必然包含它们且更大），只有失败才值得留。但最近两条**无条件**保留 —— HTTP 200 之后流才失败 / 空响应时状态码看不出来，那正是最需要导出的那份。拦截器同时捕获「根本没拿到响应」的请求（连接失败 / 超时），状态记为 null、异常摘要进导出文件，界面显示「未收到响应」；用户主动中止（传输层 `call.cancel()` 抛的 `IOException("Canceled")`）是用户意图、不含服务端信息，**不记录**，免得把真正的失败挤出缓冲。子智能体只保留最近 2 条**失败**请求（成功副本没有排查价值），缓冲在 `remove` / `pruneHistory` / `clear` 时清掉。跨会话另设总预算 `MAX_TOTAL_CHARS`（字符口径，约 12MB）：超出时丢弃最久没再记录的会话，避免「同时开很多会话」把内存叠爆 —— 请求是累积快照，单靠每会话条数上限不能约束总量。唯一入口是内置插件 `dev.kair.plugin.requestlog` 的「请求诊断」面板（`panels.requestlog`）：把本次运行内**所有项目 / 会话**的缓冲集中展示，子智能体沿 `parentId` 归到最外层会话下（与审批卡片同口径），每条给出时间 / 状态码 / 体积与「导出请求（用于错误反馈）」。不挂在消息气泡上的原因：请求是会话级、与单条消息没有稳定映射，气泡入口只能取「最近一次」，多入口还会出现口径分歧；面板同时解决了「用户不知道要长按」。导出为单个 JSON（`meta` + `request` + `response`）写入 `Delivery.PATH`，默认把 base64 图片替换成 `<base64 N chars>`，需要复现多模态问题时在对话框里勾选包含原图；「清空全部」只清内存副本，不动会话文件。

删除脚本再执行」；其余（`git commit -F -` / `cat > file`）正文剥掉再判。偏严的一侧保留：找不到结束行
（`<<` 其实出现在引号里）就整段不剥，结束行只认「分隔符 + 收尾标点」，`EOF && rm -rf src` 不算结束行
所以那条删除照旧拦。**已知覆盖不到**：接收方隔了一层（`docker exec … sh <<EOF`）认不出来。
`match()` 供调用方读**脚本文件内容**时仍按保守语义全文扫，不受这里影响。
**临时目录豁免前先折叠 `.` / `..`**：`rm -rf build/../../src` 不能凭裸 `build` 段漏过，

- 子智能体可观测 / 可中止：`SubagentManager` 暴露 `info(id)` 与 `rootSessionOf(id)`；`abort()` 会真正取消运行中的 turn（`prompt()` 把 turn Job 记为 `job`，取消后抛 `SessionAbortedException`，不会被误判成工具失败），关闭父会话会连带终止派生的子智能体。子智能体详情页渲染完整循环（模型输出 / 思考 / 工具调用与结果）；卡在审批或提问时卡片直接在详情页渲染。`ask_user` 同样带 `ownerSessionId`，等待有超时，不会让子智能体永久挂起。

## 9. proot 工作区后端（已落地）

**目标**：给 agent 一个**真实 Linux 工作区**（git / python / node / 包管理器），取代 `bash` 工具背后只有 toybox 的 `/system/bin/sh`。

**targetSdk 锁 28（关键工程决策）**：Android 10 起 targetSdk ≥ 29 的 app 被 SELinux
禁止 exec/dlopen app 私有目录里的文件——rootfs 内所有二进制（含 busybox）都无法运行。
targetSdk 28 落入 `untrusted_app_27` 兼容域保留 exec 权限（Termux 同款做法）。代价：
无法上架 Google Play（要求 targetSdk 34+）；侧载无影响。有 Root 的设备可改用 chroot
通道绕开此限制，但 proot（无 Root）通道依赖它，见 9.6。

**服务对象（勿跑偏）**：proot 环境**主要供 agent 的工具调用使用** —— `bash` 等工具在容器内跑命令，而不是主要面向人的交互式终端。人可见的终端 UI 是次要形态。接入点是**工具执行后端**（`CommandRunner` 贡献点），不是新的顶层 UI。

### 9.1 执行后端接缝（内核，已就位）

- 内核契约 `CommandRunner`（`core/tools/CommandRunner.kt`）：`run(command, workspace, timeoutSeconds)` → `CommandOutput(output, exitCode, timedOut)`；另有只读 `containerWorkspacePath`（进容器时非空，内置容器返回项目根挂载点 `/projects`）与 `containerWorkspacePathFor(workspace)`（该工作区在容器内的真实 cwd；默认回退到 `containerWorkspacePath`，旧插件语义不变）。
- `bash` 工具通过 `ToolContext.commandRunner` 取用后端，不再直接 `ProcessBuilder("/system/bin/sh", ...)`。
- **系统提示 `<cwd>` / `<workspace>` 与命令实际 cwd 对齐**：装配层取 `commandRunner.containerWorkspacePathFor(workspace) ?: workspace.path` 填入 `cwd`，另把宿主真实工作区路径填入 `workspace`。容器生效时 `cwd` 是 `/projects/<目录名>`（容器内路径，宿主进程看不到），`workspace` 是宿主真实路径；`dev.kair.prompt.cwd` 因此**同时**输出两段，未生效时只输出 `<cwd>`（两者相同）。两路径指向同一批文件 —— 宿主「工作区父目录」bind 挂载于容器 `/projects`，改一边等于改另一边；但宿主进程只能直接访问 `workspace` 那个路径（`File(cwd, …)` 在容器生效时读到的是不存在的位置）。两段均属系统提示前缀，rootfs 安装 / 卸载或执行通道切换会使其变化并失效该会话此前的前缀缓存（已知代价，见第 6 节）。`ProotCommandRunner` / `RootCommandRunner` 按「rootfs 就绪 / 已拿到 Root」判定，回退本地 shell 时返回 null。
- 贡献点：`PluginContext.commandRunner(runner)`；单例，后注册覆盖；无插件时回退 `LocalCommandRunner`（toybox）。
- `bash` 工具的 `description` 只描述稳定事实，**不写"当前是哪个后端"**（逐回合易变状态不进缓存前缀；后端信息走面板）。
- **文件后端 `isDirectory` 本地优先，不无谓升级容器**：`ContainerFileBackend.isDirectory` 对本地已可见的路径直接给本地结论（容器 `/projects/<目录名>` 与宿主工作区是同一批文件），不再为一次 `test -d` 跑一条容器命令。原实现 `local.isDirectory(path) || testFlag("-d", path)` 会让每个**已存在的普通文件**都补一次容器执行 —— `read` 工具每次读文件都会多跑一条容器命令，chroot 模式下即多一次 `su` 调用、面具随之多发一条授权通知。本地看不到的路径仍升级到容器确认；`exists` / `list` 保留原有升级路径。同类里 `list` / `walk` 早已是「本地优先」写法，此处只是对齐。

### 9.2 原生资产：自编，不引入预编译二进制

`scripts/build-proot.sh` 从源码可复现构建，产物随仓库提交到 `app/src/main/jniLibs/<abi>/`：

| 产物 | 说明 |
|---|---|
| `libproot_exec.so` | proot 主程序（PIE 可执行；talloc 静态打入；仅依赖 `libdl.so` + `libc.so`） |
| `libproot_loader.so` | 64 位 ptrace 注入 loader（`-ffreestanding` 静态 ELF） |
| `libproot_loader32.so` | 32 位 loader（容器内跑 32 位程序用） |
| `libkair_pty.so` | 用户终端的 PTY 桥（`openpty` / `fork+execve` / `TIOCSWINSZ` / 关闭回收）。**只碰 fd 与进程**：解析、编码、渲染全在 Kotlin；`scripts/build-pty.sh` 同形可复现，sha256 记在脚本头 |

- **PTY 通道的边界**：master fd 留在 Kair 宿主进程，容器里跑的只是被 `execve` 的子进程
  （chroot 档经 `su -c`、proot 档经 proot 本体，`PROOT_*` 变量经 `envp` 显式传入；模拟可用时额外有 `PROOT_L2S_DIR`，见 §9.3）。
  它与 agent 的帧协议会话是**两条独立通道**，共享 rootfs 与 `/projects` 挂载、不共享 shell 状态；
  容器帧协议**一行不改**（见 `docs/tasks/2026-11-07-用户终端PTY升级.md` §3 D3）。

- 上游锁定：termux/proot @ `a179d3e8a4e045aaa1fb8cc3284f23509d96d353`（GPL，脚本可重验）；talloc 2.4.3（sha256 校验，`scripts/proot-talloc-replace.h` 绕过 waf 交叉编译直接单文件编译）。
- **原生 unlink 路径已打补丁（U72）**：`patches/proot-unlink-eisdir-retry.patch`（sha256 记在 `build-proot.sh` 头部，checkout 锁定 rev 后由脚本 `git apply`，失败即中止）给 `PR_unlinkat` 标 `FILTER_SYSEXIT`，根治容器内 libc `remove()` 删目录恒 `ENOENT`——seccomp 加速下 unlinkat 的 exit 停止被跳过，enter 改写过的路径寄存器无人复原，musl `remove()` 的 `EISDIR` 重试复用宿主路径被二次 re-root。它替代的是工位限制「容器内建 `assembleDebugAndroidTest` 必须带 `LD_PRELOAD` shim」（[交接正文 §4](handoff/2026-11-09-proot-remove目录失效.md) 自此为历史绕法，撤除判据为真机 P3）；根因、判据与读数见 [任务文档](tasks/2026-11-09-proot-remove目录失效根治.md)。不启用 `--link2symlink`、不升 `PROOT_REV`（U72 §2 / §6）。
- 工具链：Android NDK r29，双 ABI（arm64-v8a / x86_64），API 26 与 minSdk 一致。
- 已知坑记录在脚本头部注释（loader 与主程序分两遍 make、`PROOT_UNBUNDLE_LOADER` 双传、llvm-readelf shim）。
- 打包：`useLegacyPackaging = true`（产物必须以真实文件落盘 `nativeLibraryDir` 才能 exec / 按路径访问）+ `doNotStrip`（loader 是 `-Ttext` 固定地址 ELF，构建时已手动 strip）。

### 9.3 Kotlin 侧（`core/proot`，纯 Kotlin 可单测）

- `TarExtractor`：tar 解包器（ustar/GNU/PAX），lexical + canonical 双重校验防 tar-slip 与软链穿透。
- `RootfsPatcher`：解包后补齐 DNS / hosts / group / tmp / `~/.cache`，并写 `/etc/apt/sources.list`、`/etc/apt/apt.conf.d/99kair`（Sandbox root / 关翻译）、`/usr/sbin/policy-rc.d`（阻止包 postinst 起服务）与 `/etc/pip.conf`。
- `RootfsManager`：安装状态机（下载 → 校验 `SHA256SUMS` → 解包 → 补丁 → Ready；**Ubuntu base 22.04.5**，arm64 镜像约 27.7 MB / amd64 29 MB，解包约 78 MB；ABI 不支持则降级）。镜像由**预设 id** 决定（`core/proot/ContainerMirror.kt`：阿里云默认 / 清华 / 中科大 / 华为云 / 官方；一处选择派生 apt base（arm64 走 `ubuntu-ports`、x86_64 走 `ubuntu`）、pip index 与 rootfs 下载地址）。安装补丁**覆盖写** `sources.list`（jammy / updates / security，main + universe）与 `pip.conf`，并清空 `var/lib/apt/lists`；已装 rootfs 切源由 `reapplyMirror` 即时重写（不重装）。rootfs 下载失败自动回退官方源并记日志；下载后按文件名比对同目录 `SHA256SUMS`，不一致删文件并中止，拿不到（镜像不提供 / 请求失败）只告警放行、绝不静默通过。`distro.txt` 缺失 / 非 `ubuntu` = `ReinstallRequired`（旧 Alpine rootfs 不得冒充 Ready）。
- `ProotCommandRunner`：实现 `CommandRunner`；rootfs 未就绪时**透明回退**本地 shell。容器参数：`--root-id --kill-on-exit`，挂载清单（`Mount`）逐条 `-b` bind（两条通道都只有一条：宿主工作区父目录 → `/projects`），`env -i` 隔离宿主环境，`PROOT_LOADER`/`PROOT_LOADER_32`/`PROOT_TMP_DIR` 三个环境变量定位原生库（PTY 经 `envp` 传入）。**`--link2symlink` 默认启用**（2026-11-16 起）：启动前用 `probeLink2SymlinkBoot()` 真起一次带 flag 的 proot（`sh -c exit 0`，10s 超时），起得来就用、起不来才退回原生；启用时设 `PROOT_L2S_DIR=<rootfs>/tmp/l2s`（store 必须在 rootfs 内，U68）。原因：未 root + SELinux `Enforcing` 的设备上 `untrusted_app` 对 `app_data_file` 没有 `link` 权限（内核 AVC 明确 deny），而 `dpkg` 每次运行都要 `link(status → status-old)`、覆盖已有文件还要建备份链接 —— 全部 `Permission denied`，表现为「有的包能装、有的装不上」；termux 的 proot-distro 与 OperitTerminalCore 都默认带这个 flag，由 proot 把 link 换成「符号链接 + 副本」，与设备策略无关。U69 当年关掉它是因 store 在 rootfs 外（U68）导致「`link` 成功、`stat` 被伪造、读回 `ENOENT`」，store 落回 rootfs 内后该前提已消失。**已知限制**：`/sdcard` 上 `l2s_rename` 可能跨设备 `EXDEV`（FUSE）；能力上它本就不支持硬链接。存量 rootfs 里指向 `<rootfs>/tmp/l2s` 的符号链接仍被 `unzip` / `zipinfo` 等引用（U68 时期装过的设备），**该目录不要删**，等重装自然清掉。
- `ContainerSession`：常驻会话（见 9.8）—— 单条长跑容器进程，帧协议经 stdin/stdout 下发命令 / 回读输出；`entryScript()`（容器内循环脚本）、`frame()`（帧解析）均为可单测的纯逻辑。
- `RootfsManager` 校验 `bin/sh` 用 lstat 语义（`NOFOLLOW_LINKS`）：Ubuntu 是 `bin -> usr/bin` + `sh -> dash`，Alpine 是 `bin/sh -> /bin/busybox`；`File.exists()` 跟随软链解析到设备根必然失败。
- `ProotPlugin`（`ui/plugins`）：原生库缺失（ABI 不支持）时插件整体不注册，宿主自然回退 —— 可降级，不可阻断。

### 9.6 执行通道：只剩 proot（chroot 已删除）

U78（2026-11-12，[ADR 0007](adr/0007-删除chroot会话通道.md)）把「会话执行通道」从两档收敛成
**proot 单档**：`SessionChannel` 不再有 `CHROOT`，`containerMode` 设置项下线，面板没有通道选择器。
存量 `"chroot"` / `"auto"` / 非法值在唯一读取面归一为 `"proot"`（`SettingsStore.containerMode`
只读属性），升级不崩、也不会落回真 root。

| 通道 | 实现 | 特点 | 前提 |
|---|---|---|---|
| proot | `ProotCommandRunner` | 用户态 ptrace 模拟 root；无 ptrace 之外的限制；开销 2–5× | targetSdk 28 |

- **`RootCommandRunner` 仍保留，但不再是会话通道**：它只负责需要真 root 的内部动作 ——
  挂载 bind 脚本（`buildScript`）、工作区权限迁移（`runAsRoot`）、显式提权。会话 / 终端 /
  后台任务都不再经过它；`ProotPlugin` 构造它只为了交给 `WorkspaceFileAccess` 做权限修复。
- **挂载**：proot 的 `-b` 是进程内的路径翻译，**不产生宿主挂载**；因此 chroot 时代的
  「挂载常驻 + `purgeStaleMounts` 唯一清理点」整体删除（`MountPurge.kt`、`purgePoints` 一并下线）。
  `/projects` 仍由同一份 [Mount] 清单派生，宿主父目录 → 容器 `/projects`。
- **一次性命令的后台后代**：proot 侧由 `--kill-on-exit` 收 tracee，`setsid` 也逃不出去；
  需要完成通知的长任务走 `background_task`，用户自己的常驻服务走 9.8 的持久终端。
- **「当前在哪」这个事实怎么交给模型**：容器环境变量 `KAIR_CHANNEL` 仍保留，取值恒为
  `proot`（`ContainerEnv.pairs()` 一处派生）。守则用「变量是否定义」区分「在容器里」与
  「回退到了设备 shell」（后者不经过 `ContainerEnv`，变量未定义，`LocalCommandRunner` 也不收
  `&` 的后代）。proot 的一次性进程树 / `setsid` / 常驻走 `background_task` 三条事实**已写进
  静态系统提示**（`BashTool.promptGuidelines`，U116 收敛）；不再每会话追加 `[environment]` note。
  动态 note 机制保留给 **root 授权状态**：设置页手动探测 su 后，`TurnRunner` 把 `[root]` note
  追加到历史尾部（判据：最后一条逐字相等；授权收回补否定句）。root note 只说给看得见
  `android_shell` 的会话；未探测不写、不自动弹授权。
- **显式提权（`su`）**：不在容器内注入 `su`、不给 `alpine_shell` 加 `as_root`
  （U65 随之作废）。设备已 root 时，`android_shell`（`LocalCommandRunner`）本来就能
  `su -c '<单条命令>'` 跑宿主侧提权；需要真 root 的内部动作走 `RootCommandRunner.runAsRoot`。
- proot 通道依赖 targetSdk 28 的 exec 限制，见第 9 节开头的决策说明。

### 9.7 超时与容器环境（单档对齐）

工具调用的执行分两阶段：`tool_call` 钩子（含审批闸门）**串行**执行 —— 审批闸门假定同一
时刻只有一个待批请求；工具本体按 `Tool.isParallelSafe` 分流 —— 声明并行安全的（只读类、
`subagent`、`ask_user`）在**同一回合内并发**，多个委派各自独立推进不互相排队；未声明的
（默认，含 write / edit / bash 等副作用工具）共用一把锁**按提交顺序串行**，避免同回合同一
文件的「读-改-写」互相覆盖。结果始终按原调用顺序追加，序列确定、缓存安全。
`subagent` 分两种类型（`type` 参数）：`coding`（默认，继承父会话**全部**工具）与
`search`（只保留**只读**工具 —— 按 `Tool.readOnly` 过滤，得 `read` / `ls` / `grep` / `find`
/ `read_image` / `skill`）。子智能体的系统提示与请求 schema 共用同一过滤器，两者一致。
因此超时必须是强保证：

- `bash` 工具默认 300s 超时（模型可显式传更大值；0 = 不限时）。没有默认值时，
  一条连不通的 `curl` 会让 agent 永久卡死。
- 超时的**正常路径在容器侧**执行，宿主侧强杀（`destroyForcibly`）只是脚本卡死时
  的最后兜底（T + 15s 宽限）：
  - proot：容器内 busybox `timeout -k 5 T` 包装命令（rootfs 无该二进制时跳过），
    主命令退出后 `--kill-on-exit` 收掉全部 tracee；宿主侧 SIGKILL 掉 proot 同样
    会留下孤儿 tracee。
- **用户点停止**（取消协程）走同一条终止路径：`killTree` 先枚举后代 PID，再 SIGTERM
  本体让普通进程有机会清理，最后逐个强杀。Android 运行时没有 `java.lang.ProcessHandle`，
  枚举改读 `/proc/<pid>/stat`，杀进程用 `android.os.Process.killProcess`（同 uid）。
  proot 本体与 tracee 都在应用 uid 下，不需要 root 收树。
- 容器环境由 `ContainerEnv` 统一（PATH/HOME/TERM/LANG/CI/NO_COLOR/PAGER）：
  proot 侧 `env -i` 重建。U78 起只有一张表、`KAIR_CHANNEL` 取值恒 `proot`（见 9.6），
  由 `ContainerEnvTest` 钉住「表尾只有一处通道值 + 供值取自 `MODE_PROOT`」。

**网络请求的上界（U57，2026-11-07）**：取消是协作式的 —— `call.cancel()` 打不断阻塞在
DNS 解析里的调用，而那一层此前**没有任何上界**；弱网下点停止就会永久停在 `Stopping`
（ADR 0003 的「等收尾结束才 Idle」缺一个兜底）。现在分三层：

- **前置阶段可取消且有上界**（主修，`core/ai/PreConnect.kt`）：共享客户端的 `Dns` 换成
  `CancellableDns` —— 解析丢到 daemon 线程，调用线程每 100ms 查一次「本线程上的 `Call`
  是否已取消」，取消即抛 `IOException("Canceled")`；解析一直不返回则在
  `PreConnectTimeoutMs`（5s，`core/ai/Ai.kt`）抛 `SocketTimeoutException`。
  `CallContextInterceptor` 把当前 `Call` 挂到线程局部，`PhaseEventListener` 记录
  「DNS 解析 / 建立连接 / TLS 握手 / 等待响应头」四个阶段供诊断用。
- **共享流式客户端仍然不设 `callTimeout`**：它覆盖整个调用（含读 SSE），会误杀
  「模型思考三分钟」（验收点 V7）。
- **兜底**：`abort()` 起看门狗，超过 `StopHardLimitMs`（20s，`core/agent/TurnState.kt`）
  仍停在 `Stopping` 就强制回 `Idle`，并把「停在哪一阶段、已卡多久」写进
  `Diagnostics.stopTimeouts`（「请求诊断」面板可见）。强制收口只是**止损**：卡住的协程
  仍然活着，只被从 `inFlight` 除名。U77 起 `abort()` 取消的是**活动集合里的全部串行任务**
  （过去只看一个 `job` 指针，被后起的历史编辑 / 压缩覆盖后，真正在跑的那一轮不会被取消），
  看门狗也按**整份快照**起表并逐个除名 —— 只盯一个的话，卡住的若是别的任务，上界对它没生效。
  被放弃那一轮的新增 / 覆盖 / **整份重写**都在写入面按轮次归属丢弃（不再污染下一轮前缀；
  `replaceHistory` 那条路过去刻意不在闸门内，压缩提交因此仍会改写历史），
  **配对修复除外**（ADR 0003 的取消收尾必须跑，见 §7 的写入面闸门）。
  它仍受 U43 的**作废屏障**约束：`discard()` 之后整份替换也不落盘（见 §7 的受控入口）。
  上界**不许**为了「少触发」而抬高，正常收尾经常超过它说明主修没做好。

### 9.8 常驻会话（「Linux 会话」面板）

一次性的 `ProotCommandRunner` 是「一条命令一个脚本、结束即收尾」模型，**默认装不下常驻服务**：
proot 的 `--kill-on-exit` 会收掉全部 tracee，`&` / `nohup` 启的服务随命令结束被收掉，
`setsid` 也逃不出去。要常驻的服务用下面的 `ContainerSession`。`ContainerSession`（`core/proot`）
换成**单条长跑容器进程**：挂载一次、一直持有，宿主经其 stdin 下发命令、从 stdout 读结果 ——
相当于给容器开了一个终端。

- **帧协议**：容器内循环脚本（`entryScript()`，宿主写进 rootfs `/tmp/.kair-session`）
  回显 `__KAIR_READY__` 后逐行读命令；命令在**主 shell**里 `eval`（`cd` / 变量跨命令
  保留，这是「像真电脑」的关键），每条回显 `__KAIR_RC_<code>__`。命令自身打到 stdout
  的内容直接混进同一条流，面板看到的就是连续转录；命令经 `</dev/null` 执行，避免吃掉
  宿主的命令流。
- **通道**：`buildSessionArgs(mounts)`（与一次性命令共用环境，挂载段换成清单，
  入口换成循环脚本、**不**包 `timeout`）。U78 起只有这一档（见 9.6）；
  **落不到容器就如实报错，绝不回退本地 shell**（回落会把「Android 本机 shell」伪装成
  容器，与常驻容器服务的语义相悖）。
- **挂载**：proot 的 `-b` 是进程内模拟绑定，会话启停都不产生宿主挂载；
  chroot 时代的 `buildPurgeScript` / `purgePoints` 随 U78 下线（见 9.6）。
- **网络**：容器与 App **同网络命名空间**（无 `unshare -n`），容器内监听
  `127.0.0.1:<port>` 即全设备可见，用户可用设备浏览器打开
  `http://127.0.0.1:<port>`。
- **归属与入口**：会话由 `ProotPlugin` 创建并发布到
  `AppContainer.containerSessionHost`（`core/proot/ContainerSessionHost.kt`）；
  独立内置插件 `TerminalPlugin` 消费它，只贡献面板 `panels.terminal`（对话页顶部
  快捷槽位已于 2026-10-30 移除，面板仍从插件页进入）。
  两个插件各自可禁用：禁用 proot 会 `clearAndStop()`，禁用终端只回收 UI、不杀会话。
  系统提示里由 `dev.kair.prompt.capabilities` 段告知 agent「容器是可选依赖」。
- **用户终端（PTY，U59）**：`containerSessionHost` 有第二个 `StateFlow`（`pty: StateFlow<PtySession?>`），
  与帧协议会话**同属一个 host** —— 两者共享 rootfs 与 `/projects` 挂载，启停必须同步；
  `replace()` / `clearAndStop()` / `restart()` 同时管两条通道（U60 的「重启会话」按钮因此一次换掉两者）。
  面板形态是 Termux 式：终端网格占满面板，点一下聚焦隐藏输入层并弹软键盘，无独立输入框，
  底部两行扩展按键（Termux 默认布局，CTRL / ALT 一次性修饰，FN 切 F1–F12）；
  PTY 起不来或 shell 退出时回退行式终端（`ContainerSession.exec()` 仍是 agent 通道，不删）。
- **Linux 进程面板**：`ProotPlugin` 贡献 `panels.processes`（
  `ui/plugins/builtin/ProcessPanel.kt`），用一次性容器命令扫描 `/proc`，**只列带
  `KAIR_CONTAINER=1` 标记的进程**（标记由 `ContainerEnv.MARKER` 注入），显示
  PID / PPID / RSS / 命令行。探测会跳过自己的祖先链与
  `KAIR_PROBE_PID` 子孙，避免把 `proot` / 探测命令本身列出来。持久进程的
  `shell` 标为受保护，结束它请走工作区的停止按钮；普通服务可单进程结束
  （TERM → 5s → KILL，结束前复核标记，防止 PID 复用误杀）。刷新是手动快照，
  每次探测都要起一次 proot，不做自动轮询。
- **App 代际回收（R1，2026-10-31）**：容器进程不是 App 的子进程（proot 由原生库起），
  App 进程死亡时 Android 不会连带收掉；而命令级回收（一次性命令的组收尾、
  `ContainerSession.stop()` 的 `killTree`）都要求「App 还活着、有人在跑收尾」。因此：
  - `ContainerEnv` 增加**代际标记** `KAIR_INSTANCE=<本次 App 进程的随机 token>`，进 `env -i` 事实源；
  - 一次性命令 / 维护脚本在**挂载之前**扫 `/proc`：带 `KAIR_CONTAINER=1` 且
    `KAIR_INSTANCE` 不等于当前的一律 TERM → 1 秒 → KILL（`ContainerProcesses.reapCommand`，
    由 `RootCommandRunner.buildScript` 的 `reapStale` 参数接线）；
  - **`KAIR_INSTANCE` 缺失也算上一代** —— 本批上线前的存量进程没有这个变量，靠这一条才能在
    第一次启动时把历史遗留一起清掉；
  - 面板另有「全部结束」（`ContainerProcesses.killAllCommand`）：只清**本代**、保留会话 shell
    （由工作区停止按钮负责）、靠 `KAIR_PROBE_PID` 跳过自己与子孙（它自己在容器内执行、带本代标记）。
  - **「自启」进程**（用户登记，U56 单模式）：`ProtectedProcessStore` 落
    `<storageRoot>/protected-processes.json`，存的是**命令行**（PID 重启后必变，记了等于没记）。
    语义是「Kair 启动时自动拉起」，**不是**跨 Kair 重启永续：下次会话进入 `Running` 后由
    `ProtectedProcesses.restoreCommand` 逐条判「还在不在跑」：在跑只打一行日志，
    **不在跑才** `setsid sh -c "<cmdline>"` 拉起 —— 新进程带当前代
    `KAIR_INSTANCE`，状态每次都是新的。
    面板「全部结束」仍按命令行**完全相等**跳过登记命令（用户对本代进程的显式保护，
    不是死亡豁免；不做子串 —— 否则 `:8080` 会顺带保护 `:80801`）；启动代际清扫
    （`reapCommand`）仍传登记名单，作为上一代残留的兜底。
    它不是守护进程：只在会话就绪时判一次、起一次，崩了不会自动重启。
  - 边界：Android 没有可靠的退出回调（`onTerminate` 只在模拟器调用），App 被强杀后
    到下次启动之间旧进程仍在跑，这是固有限制不是遗漏；没有 `KAIR_CONTAINER=1` 的逃逸进程
    （自己 `env -i` 重造环境）清不掉，本批不猜宿主 `/proc` 的归属。
  - **U78：chroot 代际收尸人（U55）已删除**（`reaperScript` / `deathSweepScript`）——
    它只服务 chroot 档；现在没有整段会话以真 root 运行，也就不存在需要 root 守护进程收的树。
- **为什么进程面板要靠标记**：容器没有 PID namespace，容器里的 `/proc` 就是宿主
  进程表；直接 `ps` 会混进 Android 系统 / 其他 App 的进程。标记过滤是当前模型下
  唯一安全的做法（见 9.6 与本节已知限制）。标记分两层：
  `KAIR_CONTAINER=1` 回答「是不是容器进程」，`KAIR_INSTANCE` 回答「哪一代」—— 后者只用于
  跨 App 进程的清理，面板展示仍只按前者过滤（上一代的进程在面板里也看得见，才手动杀得掉）。
- **终端面板**：`TerminalPanel` 只做纯终端交互 —— 会话状态、终端转录、命令输入
  （IME 发送）与 ↑↓ 历史回填。暗色等宽终端风格，贴底滚动。持久进程**常开**：
  没有启动 / 自动启动开关；`ProotPlugin.activate` 在 rootfs 就绪时自动拉起，
  未就绪则等安装完成后拉起，失败时「Linux 工作区」面板给一次重试。
  状态行旁有「重启会话」（U60：**Running / Error / Stopped 三态可点**，
  `stop()` → `start()`；Starting / Stopping 过渡态禁用）；命令超时后 `suspectStalled`
  置位，面板显示「上一条命令超时，会话可能已卡住」提示。
  `SessionCard` 只显示状态、通道与「项目根目录：/projects」；不再有「已挂载项目数」
  （挂载只有一条）。
- **共享终端语义（C1 / 2026-10-30 简化为单挂载）**：会话与 agent 的 `bash` **挂同一份**
  —— 宿主「工作区父目录」→ `/projects`（`ProjectMounts.kt` / `Mount.kt`）。项目是它下面
  的真实子目录，目录名由项目名生成（`core/storage/Storage.kt` 的 `projectDirName`）。
  起始目录 `/projects`，启动日志打一行宿主根目录。终端与「当前会话 / 当前项目」**无关** ——
  切换项目不重启会话（原 `bindingChanged` 守卫与 `SessionBinding.kt` 已删除，`AGENTS.md` §10.3）。
  **新建 / 改名 / 删除项目都不需要重新挂载**：chroot 与 proot 同时即时可见（旧版按项目
  挂载 + chroot 热挂载、proot 重启才生效的实现已整体删除）。代价是 agent 能看见其它项目
  目录 —— 这是负责人 2026-10-30 的明确取舍，作用域改由系统提示的 `<cwd>` 表达，不再以
  挂载隔离。项目改名同时搬目录：该项目有会话在忙（回合 / 排队 / 后台任务未投递）时拒绝，
  空闲会话先关闭再搬，历史在存储里、重开按新路径加载（`ProjectOps.kt`）。
- **已知限制（v1）**：行式终端没有 PTY / Ctrl-C；单条命令有 **120s 上界**（U60，与
  `SseIdleTimeoutMs` 同量级），超时只回结果 + 置「疑似卡住」标记，**不撤销队列条目**
  （下一条命令仍按帧严格配对），卡住时用面板的「重启会话」恢复；命令读不到 stdin，
  vim / top 等全屏程序不可用；持久终端若正 `cd` 在被改名的目录里，`pwd` 仍显示旧路径
  （dentry 不变），新命令请重新 `cd`。

### 9.9 工作区权限（设置页手动入口）

U78 起会话只有 proot 一档（见 9.6），`alpine_shell` 落盘归应用 uid，**不再产生 root 属主文件**。
权限修复入口仍保留，兜的是另一类来源：用户显式提权（`android_shell` 里 `su -c …`）或历史版本
留下的 root 属主文件。应用进程用 `java.io.File` 直接读会 EACCES（典型：记忆插件读
`.kair/memory.md`）。**rootfs 内部本就是 root 属主，属正常状态，不作处理**；只修工作区 /
回收站这一层。

- **判定**：`WorkspacePermissionRepair` 检查目标路径及其**子条目**的 `canRead` / `canWrite`
  （目录还要 `canExecute`）。父目录健康不代表子文件健康（root 常只替换了 `.kair/memory.md`
  一个文件），所以精准模式会下钻，单次最多 4000 个条目；目录自身坏掉时不再下钻。
  只有应用真的碰不了的路径才触发修复；全部正常时不启动任何子进程。
- **范围**：默认 = 每个项目工作区的 `.kair` + 已安装插件 `declareData` 声明的路径 + 回收站
  （`<storageRoot>/trash`，容器内挂载为 `/trash`）。仍不遍历整棵工作区（大仓库 /
  `node_modules` 会拖慢冷启动，构建产物也无需归应用）。
- **修复**：**走真 `su`**（`RootCommandRunner.runAsRoot`，宿主绝对路径），
  执行 `chattr -i -R <路径>; chown -R <应用 uid> <路径>; stat -c %u <路径>`。
  必须先清 immutable 标志：`chattr +i` 的条目连 chown 都会失败；精简 rootfs 没有
  `chattr` 时由 `command -v` 短路，仍继续 chown。**末尾的 `stat` 是自证**：
  proot 的 `fake_id0` 会让 chown 返回 0 而属主仍是 0，旧实现只看退出码，界面报「已修复」——
  现在只有属主真的变成应用 uid 才计 repaired（判据 A-5 / C-5）。
  拿不到真 root 或 chown 失败时，降级为**应用侧重建**：把可读文件读出 → 同目录临时文件 →
  `rename` 覆盖。替换 root 属主的文件只需要父目录可写，无需 `CAP_CHOWN`，产物归应用所有；
  不可读（600）、目录、符号链接、超过 4 MiB 的不降级，如实计入失败。
- **预防**：proot 会话的 `entryScript()` / 一次性命令的 `umask 000` —— 新建文件默认 666、
  目录 777，应用进程可直接读写，无需事后 chown。umask 只影响此后新建的 inode，不改已有文件
  与属主；rootfs / 工作区都在 App 私有目录内，Android 沙箱仍隔离其他应用。
- **回收站与不可变属性**：回收站位于**所有工作区之外**（宿主侧是 Kair 私有目录），
  容器里只通过 bind 挂载以 `/trash`（`$KAIR_TRASH`）出现，在自检范围内。删除时
  `ContainerFileBackend` 先本地删，失败升级容器 `rm -rf`；仍失败则执行
  `chattr -i -R` 再删 —— `chattr +i` 的条目连 root 都删不掉。移动 / 恢复同样在
  `mv` 前清标志，否则 immutable 文件无法移出回收站。
- **入口**：仅设置页「工作区文件权限」提供手动入口（默认精准范围 / 可修当前项目整棵
  工作区）。启动界面不再做权限自检：新文件本就归应用，历史遗留条目按需手动修复即可。
- **提示词**：`<kair>` 能力段告知 agent 回收站位置（不在 `/projects` 下）、
  umask 000 下新文件默认可读写（显式 600 仍可能锁死 App）以及各面板的分工，
  并禁止对工作区 / 回收站条目设 `chattr +i`。
- **写入侧兜底**：`ContainerFileBackend.writeText` 本地写失败时先「同目录临时文件 +
  rename 覆盖」（目录可写即可把 root 文件换成应用自己的），再升级容器并在落盘后
  `chmod 644`，见 9.1 与 `FileBackend`。

### 9.10 MCP 服务器（已落地）

MCP（Model Context Protocol）把外部工具接进 agent，实现为**内置插件 + 内核侧运行时**：
`core/mcp`（协议 / 传输 / 连接管理，不依赖 Compose）与 `McpPlugin`（面板与管理工具）。

- **传输**：Streamable HTTP（`Mcp-Session-Id` + JSON 或 SSE 响应）、旧版 HTTP+SSE
  （GET 事件流的 `endpoint` 再 POST），以及 **stdio**（在 proot 容器内启动子进程，
  stdin/stdout 走换行分隔 JSON-RPC）。stdio 不经过常驻会话 —— 后者的行式帧协议会与
  JSON-RPC 冲突；`ProotCommandRunner.spawnProcess` 复用同一套挂载与环境，进程由
  `McpProcessHost`（ProotPlugin 提供）创建。
- **工具命名**：`mcp__<server>__<tool>`，非 `[A-Za-z0-9_]` 字符归一化为 `_`，避免与内置
  工具 / 其它服务器撞名。`inputSchema` 的 `#/$defs/...` 引用先内联展开（部分 provider
  不接受悬空 `$ref`），再删掉 `$defs`。
- **连接管理**：每台服务器一份独立状态机（状态 + 互斥锁 + 重试任务），失败按
  1s→2s→…→30s 退避，最多 5 次；一台连不上不影响其它服务器。断开由传输的
  close 回调上报，状态回到 Error 并安排重连。
- **工具注册**：MCP 工具是动态集合，不进插件注册表 —— `AppContainer.resyncTools()`
  在插件工具之后追加 `mcp.tools()`。连接成功 / 断开 / 单工具开关都会触发重建，已打开
  的会话下一回合即生效（与工具开关同一语义）。
- **缓存前缀影响**：工具清单进入系统提示与请求 schema，因此连接/断开服务器会作废该
  会话此前的前缀（低频操作，与手动开关工具同类代价）。顺序确定性由两条排序保证：
  服务器按名字排序、每个服务器内工具按名字排序。
- **配置真源**：`SettingsStore.mcpServers`（JSON-in-prefs，与 `saved_models` 同模式）。
  支持 `mcpServers` 兼容格式导入（Claude / Cursor / pi），同名整条替换。
  `disabledTools` 按服务器记录，编辑服务器时保留原开关。
- **agent 安装入口**：`mcp_list`（只读）与 `mcp_manage`（add / remove / enable /
  disable / test / reload / import）。`mcp_manage` 需要审批且**不允许永久放行** ——
  安装 stdio 服务器等价于在容器内执行任意命令，与 `install_plugin` 同一信任边界。
- **审批类别**：MCP 工具的 `annotations.readOnlyHint` / `destructiveHint` 映射为
  `READ` / `DELETE`，无声明按 `EXECUTE`；因此只读工具不弹窗、破坏性工具跟随删除审批开关，
  其余可在审批面板用「执行类工具需审批」统一拦截。
- **首版边界**：不含 OAuth 2.1、resources / prompts、服务端主动推送的 GET 流
  （`tools/list_changed` 靠重新连接 / 面板重进感知）；远端凭据用自定义请求头。
- **全局状态约定**：`McpManager` 归属整个应用，随进程存活；配置变化即时 `reconcile()`，
  插件禁用时 `closeAll()`，容器插件禁用时清空进程工厂并只断 stdio 会话。并发上同服务器
  串行、跨服务器并行；UI 只观察 `status` 流，不直接持有连接。

### 9.11 挂载布局：一次挂载（2026-10-30 起）

宿主**工作区父目录**整棵 bind 到容器 `/projects`；项目是真实子目录，目录名由项目名生成：

```
宿主                                       容器
.../projects/workspaces/        ──bind──▶  /projects
├── 程序员/                                 ├── 程序员/    ← 与宿主同一批文件
└── 测试1/                                  └── 测试1/
```

- **目录名 = 项目名清洗后**（`projectDirName`）：`/` `\` 与 Windows 保留字符换 `-`，
  首尾空白 / 点去掉，最长 60 字符，空名退回 `project`；与现有目录撞名追加 `-2`、`-3`。
  展示名另有唯一性约束（忽略大小写），正常情况不需要后缀。id → 目录名的映射在
  `projects/project-dirs.json`：改名后或映射丢失时按名字认领磁盘目录，旧版 UUID 目录
  在启动时搬成名字目录（迁移失败则暂时沿用 UUID，下次启动再试）。
- **为什么只挂父目录**：旧版按项目挂 `/projects/<slug>`，新建项目要补挂、改名 / 删除还要懒卸载。
  父目录一次挂载后，新建 / 改名 / 删除都只是
  文件系统操作。代价：agent 能看见并修改其它项目 —— 负责人 2026-10-30 明确接受，
  作用域改由系统提示的 `<cwd>` 表达，不再以挂载隔离。
- **单档同一份清单**：`bash` 与常驻终端都只用 `workspaceMounts()` / `projectsMount()`
  （`Mount.kt`）；一次性命令的 cwd 是 `/projects/<目录名>`，常驻会话起始目录 `/projects`。
  proot 的 `-b` 把同一个宿主父目录翻译进容器（进程内模拟，不产生宿主挂载）。
- **回收**：proot 的挂载随进程消失，**不需要清理点**；chroot 时代的挂载常驻 +
  `buildPurgeScript` / `purgePoints` 已随 U78 下线（见 9.6）。
- **改名**：目录随展示名一起搬（`ProjectStore.rename` 先搬目录再写索引，写失败回滚）。
  `ProjectOps.renameProject` 要求该项目**没有忙会话**（回合 / 排队 / 后台任务未投递），
  先把空闲会话关掉再搬 —— 会话持有旧路径，历史在存储里、重开按新路径加载。
- 与 agent 的边界见 9.8「共享终端语义」。

### 9.12 Agent 后台工具任务（`background_task`）

持久进程（9.8）解决「进程怎么活」，本节解决「agent 怎么把长命令放到后台跑、
完成后再回到循环」。两者不是一套东西：前者面向用户与终端，后者是工具调用。

- **工具与归属**：`background_task` 由 `ProotPlugin` 注册
  （`ui/plugins/builtin/BackgroundTaskPanel.kt` 导出面板与工具工厂），执行交给
  `app/BackgroundTasks.kt` 的 `BackgroundTaskManager`。工具属 EXECUTE 类，走现有
  审批闸门；**子智能体会话直接拒绝**（其 id 不在 `SessionRegistry`，完成通知没有接收方）。
- **执行（U60 改）**：宿主侧直接起一个**前台、不等待**的容器进程，**不再经会话 `exec`**
  （会话 shell 卡死不再连带后台任务）。proot 档独立 `ProcessBuilder` 实例
  （proot 活着 = 任务活着，`--kill-on-exit` 收尾）。任务脚本 `<id>.sh` 写
  `<workspace>/.kair/tasks/`，runner `<id>.run.sh` **在容器内**把输出重定向到 `<id>.log`
  （宿主进程的 stdout 是没人读的管道，写满 64KB 会阻塞任务），退出码写 `<id>.rc`；
  宿主只轮询 rc，不轮询会话 shell、不污染终端转录。收尾走宿主侧进程树：
  proot `killTree()`，chroot 经 root 递归收树；任务进程带 `KAIR_CONTAINER=1` 与
  `KAIR_INSTANCE`，残留由下一代会话启动清扫。工作区 → 容器路径用
  `ContainerSession.mountedMounts` 的父挂载（`<base> → /projects`）加相对路径得到
  `/projects/<目录名>`（`containerPathOf`）。
- **完成判据（U49 改）**：`.rc` 由容器内 `trap` 在退出前写出，而 SIGKILL / 崩溃 / 任务自杀都不执行
  trap —— 只看 `.rc` 会让这类任务永久停在 RUNNING（`hasRunning` 恒真 → 会话不淘汰、保活常开、
  通知永不投递）。watcher 的判定顺序固定为 **`.rc` → 宿主进程存活 → 超时**：先判存活会把
  「刚好正常退出」记成异常终止，先判超时会把「进程已死」报成超时。存活为假时**再等一拍重读一次
  `.rc`**（防「进程退出 ↔ 落盘」的窗口），仍无才落新终态 `TERMINATED`（不是 `FAILED`：没有退出码；
  不是 `CANCELLED`：不是用户干的）。存活判定不在 `timeoutSeconds > 0` 分支里，`timeout=0` 的常驻
  任务同样要能落终态。`kill()` / `killAsync()` 先探存活，已死只摘句柄、不发信号（chroot 档按 pid
  发 su 信号，pid 复用会误伤无关进程）。探针语义：chroot 档 `su` 等子进程 ⇒ `su.isAlive`；
  proot 档 `proot` 是 tracee 的父、`--kill-on-exit` 让两端同步退出 ⇒ `proot.isAlive`。
- **限额**：单会话最多 2 个运行中；内存保留最近 20 个任务，**截断只丢已终态的**
  （运行中的永不挤出 —— 一旦出列就再也没有完成检测 / 超时 / 取消入口，进程却还在跑），
  20 条全在跑时直接拒绝启动；任务文件在启动时按目录清理（含上一次进程留下的孤儿，
  因为任务表只在内存）；默认超时 1800s、工具参数上限 3600s；脚本用 `ulimit -Sf`
  给任务进程设**单文件 soft 上限** 1.5 GiB（进程级全局：日志与构建产物同受此限；只限日志需另换机制）。
  **只降 soft 不降 hard**：抬 hard 要 `CAP_SYS_RESOURCE`，而 proot 档的任务进程是 app uid fork 的
  「模拟 root」（`CapEff=0`），hard 一旦压低就永久抬不回来（真机：128 MiB 处收 SIGXFSZ、
  `ulimit -f unlimited` 报 EPERM）。留 hard 在原值，任务要写更大的单文件时自己
  `ulimit -f unlimited` 抬 soft；这条口径对 chroot 降权（U65）后的两条通道同样成立，
  也写进了 `background_task` 的工具描述（模型侧可见，用 `MAX_FILE_SOFT_LABEL` 换算，不手抄数字）。
- **并发写入**：任务表的所有写入（`start` 插入、watcher / `cancel` / `cancelAll` 落终态）都走
  `BackgroundTaskTable.kt` 的 CAS 循环；**禁止**用读-改-写快照写回 —— 跨会话并发 `start`
  会丢记录，`start` 与 watcher 收尾重叠会把终态写回 RUNNING（`hasRunning` 永久为真，
  会话不判空闲、保活不释放）。`start` 插入后复查 `sessionExists`，覆盖 `launch` 期间会话被
  关闭、`cancelAll` 没看到新任务的窗口。
- **完成回注**：结果**不是第二个 tool result**（一次 tool_call 只能配一个结果，补第二个
  会让历史变坏）。`BackgroundTaskManager` 通过 `AgentSession.steer(text, systemNote = true)`
  追加英文完成通知（退出码 + 日志尾部）：**会话空闲时**它等价一次 `send`，同时就是
  「唤醒空闲会话」；**会话在跑时**它进 `QueueKind.STEER`，在**下一步请求装配前**并入历史。
  用户按停止后同样会投递（停止中止的是当前回合，不是后台任务）。
  **不等空闲（2026-11-01 U18 改）**：老实现 `first { Idle }` 把通知扣到回合结束 ——
  真机上一条连发工具的长回合里三个任务先后完成，三条通知被一起挂到「引导中」、
  且只有第一条能起唤醒回合（其余落进只在「本回合要结束」时排空的 `FOLLOW_UP`，于是滞留）。
  随「等空闲」一起删掉的还有它的 10 分钟上限与 U17 为绕过它加的 `awaitNote` 开关。
  投递后核对历史 / 队列，没落地就补投（最多 3 次）；**「已进队列」算已送达**的前提是
  `TurnQueue.clear()` 保留 system note（用户输入照旧清掉），否则返回成功的通知会被
  abort 静默抹掉。
  **会话关闭不投递**：`SessionRegistry.Cleanup.BackgroundTasks` 会先 `cancelAll`，
  杀进程组并停止通知。
- **会话不淘汰**：有运行中任务、或通知还在投递中的会话都不算空闲（`AppContainer` 的
  `describe`；`delivering` 与终态在同一次 CAS 落表，投递返回即清除），否则 LRU 淘汰会让
  完成通知失去接收方。保活条件同样把运行中任务算作活跃（见 §12）。
- **界面可见性**：「引导中」面板只列**用户自己**排队的消息
  （`Composer.visibleQueue` 过滤 `isSystemNote`）—— agent 的通知按步并入、不该出现在
  用户输入区，老写法把它列出来且提示文案对 `FOLLOW_UP` 是错的措辞，用户读成「消息发不出去」。
- **缓存影响**：新工具只改一次工具清单（既有会话会收到一条工具集变化提示）；完成通知
  只追加在历史尾部，不改写前缀。工具描述 / 通知正文均为英文。
- **已知限制（v1）**：任务只在内存，进程被杀 / App 重启即丢失（日志文件仍在）；命令若
  `exec` 或外部 SIGKILL 导致脚本没写 rc，由存活判据落 `TERMINATED`（U49 之前会一直等到超时，
  `cancel` 除外）；没有 PTY / stdin；
  容器无 PID namespace，任务进程在 `/proc` 里与宿主同表（标记过滤见 9.8 的进程面板）。
  chroot 档取消依赖 root 收树脚本拿到 pid；脚本刚起、pid 还没落盘时退回
  `Process.resolvePid()`（U67 起 Android 上从 `UNIXProcess.toString()` 兜底取 pid；
  形状不匹配时仍按 0 退回「只杀本体」，见 U67 任务文档 §10），这类残留由下一代会话启动清扫兜底。

## 10. 动态插件与技能（已落地）

「能力皆可插拔」的最后一块：让 **agent 自己**在运行期扩展能力，同时不破坏内核边界
与缓存契约。插件 API 细节见 `docs/插件接口契约.md` 第 9、10 节。

### 10.1 技能（Skills）：渐进式披露

- 一份 `SKILL.md` = 一个技能；**只有「名称 + 描述」进系统提示索引**（确定性排序，
  缓存友好），正文由模型按需经 `skill` 工具读入 —— 正文经工具结果进入上下文尾部，
  前缀不动。
- 技能源：存储根 `skills/` 目录（用户放）、动态插件（`manifest.skills` 指向插件内
  目录）、内置技能（`plugin-authoring`）。同名时先加入者胜。
- **逐文件容错**：坏 `SKILL.md`（不可读 / 内容非法 / 扫描中被删）只让该技能缺席。
  原因按技能目录名记进 `SkillRegistry.loadFailures` 供诊断面板展示，每次扫描**整表替换**
  —— 修好后旧记录随之消失。跳过必须留痕：静默丢弃会让「技能没生效」变成只能靠猜的故障。

### 10.2 动态插件：数据 + 脚本，无代码加载

- 形态：`plugins/<id>/manifest.json` + 脚本文件。宿主解释清单注册贡献点
  （工具 / 系统提示段 / 技能根），**不加载 dex / 原生库** —— 规避 Android
  可写目录执行限制，也不引入与宿主的编译期耦合。
- 脚本工具经**当前命令执行后端**运行（proot 就绪时即在 Alpine 里），参数经
  `KAIR_ARGS`（JSON）环境变量传入、单引号转义防注入。
- 覆盖语义与静态插件一致（后注册者胜）：动态插件可替换内置工具（如脚本版 `bash`）。

### 10.3 信任边界（安全模型）

- `install_plugin` / `uninstall_plugin` 由宿主在执行注册表**最后**注册：
  任何插件都无法覆盖它们；两者 `requiresApproval = true` 且 `approvableForever = false`
  —— 安装 / 替换插件等价于任意代码执行（脚本能覆盖命令后端），**必须**用户逐次或
  逐会话确认，永久放行被结构性禁止。
- 宿主校验清单：`manifest.id` 与目录名一致、引用脚本存在、id 无路径穿越。
- 审批拒绝时以 `blockReason` 回给模型（复用既有工具阻断语义），不重试。
- 上条约束的是 **agent 代模型发起**的安装。用户在插件页亲手经文件管理器选择
  `.kplug` 的安装（`DynamicPluginHost.installPackage`）是**用户显式操作**，不经审批
  闸门——意图与「点开安装包」一致。

### 10.4 热发现：会话无需重建

动态插件安装 / 卸载 / 重载后，**已存在的会话无需重建**即可立即看到变更
（默认开启，无开关）：

- 宿主 `DynamicPluginHost` 在 `install` / `uninstall` 后触发 `resync` 回调，重建执行
  注册表的终序（内置 → 插件贡献 → 宿主 `install_plugin` / `uninstall_plugin`）。
- `PluginRegistry` 的各贡献点查询（`tools()` / `systemPromptContributors()` /
  `contextStrategy()` / `commandRunner()` / `storage()`）本身就是**实时查询**，不做
  快照缓存。
- `AgentSession` 把「随请求解析」的提供者（`contextStrategyProvider` /
  `commandRunner` / `filesProvider`）在**每次请求装配 / 每次工具调用**时求值，
  而非构造时固化；每发请求的输入由 `inputsProvider` 解析成一份不可变快照
  （`ResolvedRequestInputs`，U42），系统提示在其中经 `SystemPromptBuilder`
  重新拼装。于是旧会话下一回合就带上新插件的工具 / 提示段 / 策略。
- **手动触发**：内置斜杠命令 `/reload` 重新扫描 `plugins/` 并重装全部动态插件
  （重读磁盘上的清单 / 脚本），用于插件文件被外部改动后主动触发更新 —— 与
  `install_plugin` 的热发现同一路径，旧会话无需重建。
- **代价（已知且接受）**：新增 / 移除插件会改变系统提示与工具列表这类**缓存前缀**
  内容，使该会话此前的前缀缓存失效（`CacheInspector` 面板会如实显示命中率回落）。
  这是「运行期热变更」与「前缀字节稳定」两条目标之间的取舍，用户已明确接受。
  未发生插件变更时，前缀仍逐回合字节稳定。

### 10.5 兼容性巡检与装载失败收敛

插件 dex 独立编译，宿主升级可能带来**类级**不兼容（`targetApi` 检查管不到）：

- **编译侧**：`:plugin-api` / `:app` 固定 `-Xjvm-default=all-compatibility`；契约新增成员
  必须带默认实现；破坏性变更才提升 `KairApi.VERSION`（详见 `docs/插件接口契约.md` 10.5）。
- **运行侧**：`PluginBinaryCompat` 在装载后扫描插件入口与贡献对象（工具 / 传输层 / 提示段 /
  策略 / 存储 / 命令后端），对照当前契约的抽象成员找出缺失项，按插件 id 暴露给插件页。
- **失败收敛**：`activate()` 抛 `AbstractMethodError` / `NoSuchMethodError` /
  `NoClassDefFoundError` 时被 `runCatching` 收住，记入 `loadFailures`；插件页单列
  「无法加载」并提供「重试 / 删除」—— 不允许链接错误冒泡打断启动。
- **可见性**：已安装但不兼容的插件在其列表行显示红字（缺失成员名），不等某次调用才闪退。
- **混淆**：`app/proguard-rules.pro` 保留 `dev.kair.plugin.api.**` 与
  `core.{agent,ai,model,plugin,storage,tools}.**`；开启 `isMinifyEnabled` 后不得删除这些
  keep 规则（插件 dex 与宿主不共享混淆映射）。

## 11. 界面（Compose，已落地）

- **单层落点**（U116 删旧首页）：冷启动直接落三者之一 —— 上次项目的最近会话 /
  该项目的新会话页（0 会话）/ 无项目页（一个项目都没有）。项目与会话切换收进
  ☰ 推屏抽屉（项目段 → 会话段），不再有独立的「项目 / 会话列表」首页。
  所选项目经 `SettingsStore.lastProjectId` 记忆；点 0 会话项目、新建项目成功都直接
  落到该项目的新会话页。
- **路由**（`ui/KairNav.kt`）：`no-project` / `chat/{projectId}/{sessionId}` /
  `settings` / `plugins` / `panel/{panelId}`。
- **折叠渲染**：一个 assistant 回合内的思考与**全部工具调用**默认折叠；工具调用按语义
  归类为一句概览（`toolGroupCounts`：「执行 3 次命令」「编辑 2 个文件」，混类以
  `、` 连接），展开后才显示每次调用的输入与输出。被收纳的输出不再单独成卡，仅
  **孤儿结果**（压缩切点切掉调用但结果仍在）仍单列渲染。
- **压缩提示**：`AgentSession.lastCompaction` 暴露最近一次压缩的 token 变化（`seq`
  单调递增以穿透 `StateFlow` 去重），对话页以 Snackbar 提示「上下文已压缩：X → Y」，
  会话顶部的检查点卡片保留摘要正文。这是一次性事件：UI 展示后调用
  `consumeLastCompaction()` 置空 —— 会话对象长期存活而界面会重建，只靠界面级
  remembered 去重会在离开 / 重进会话时丢失并反复弹。
- **插件安装入口**：插件页「安装插件」按钮经系统文件管理器（SAF `OpenDocument`）选择
  `.kplug` 包，`DynamicPluginHost.installPackage` 读清单取 id 后走 `installFrom` 装载。
- **子智能体详情**：子智能体列表项可点进详情页，显示完整循环（模型输出 / 思考 / 工具调用
  与结果）与运行时长；审批 / 提问卡片在详情页就地渲染，卡住时可直接放行，并可从详情页终止
  —— 不必退回父会话猜「它到底卡在哪」。
- **插件问题可见**：已安装但不兼容的插件在该行显示红字（缺失的契约成员）；装载失败的插件
  单列「无法加载」，带「重试 / 删除」。问题在插件页暴露，不靠调用时的闪退暴露。

## 12. 后台常驻（前台服务，已落地）

让应用切到后台后继续跑，正规机制是**前台服务 + 常驻通知**，**不是无障碍服务**
（无障碍需用户手动开启、面向辅助操作，不是维持后台的手段）。

- **服务**：`app/KairForegroundService`（`foregroundServiceType=dataSync`）在通知栏挂一条
  常驻（ongoing、低优先级、静音）通知，把进程提升为前台优先级；任务执行期间再持一把
  `PARTIAL_WAKE_LOCK`，避免熄屏后 CPU 休眠拖慢或挂起任务。`START_STICKY` 便于系统回收后重建。
- **起停策略**：内置插件 `dev.kair.plugin.keepalive`（「后台常驻」面板）把「常驻开关」、
  `AppContainer.runningSessions` 与正在跑的后台工具任务（§9.12）合成 —— 任一成立即维持
  服务，三者皆无则停止。故即使不开常驻，长任务运行期间也能获得前台优先级。
- **权限**：清单声明 `FOREGROUND_SERVICE`(+`_DATA_SYNC`) / `POST_NOTIFICATIONS` / `WAKE_LOCK` /
  `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`。因 `targetSdk = 28`，通知权限默认放行；面板另提供
  「忽略电池优化」「通知设置」两个跳转按钮兜底。
- **可插拔**：常驻开关经声明式设置面板（`SettingField.Toggle.onChange`）驱动，属于插件能力而非内核。
