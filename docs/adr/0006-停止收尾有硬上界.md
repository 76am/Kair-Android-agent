# 0006. 停止收尾有硬上界（更正 0003 的「不加超时」）

- **状态**：提议（U57 B 审 2026-11-07 代拟，**待负责人批准**；批准前它只是把已有实现记成决策）
- **日期**：2026-11-07
- **取代关系**：**不推翻** [0003](0003-停止要等取消收尾结束.md) 的结论（正常路径仍是「等取消收尾结束才 Idle」），
  只更正它「后果 / 代价」里那一句：「`stopping` 本身没有上限……不额外加超时」。

## 背景

0003 写下「不加超时」时，理由是两条：一是「延时是猜的，猜短了重演竞态」，二是当时确实没有
别的办法让「新一轮」与「仍在收尾的旧轮」不并发。U57 的真机现场把另一件事摆到眼前：
取消是**协作式**的，`call.cancel()` 打不断阻塞在 DNS 解析里的调用，而那一层此前没有任何上界 ——
弱网下点停止会永久停在 `Stopping`，负责人实测十分钟只能杀 App。

「永久」和「久」不是一回事：0003 的代价段把它当成用户体验问题，实际是**可用性故障**。

## 决策

1. `abort()` 之后给一个硬上界（`StopHardLimitMs` = 20s，`core/agent/TurnState.kt`）：到点仍停在
   `Stopping` 就强制回 `Idle`，并留一条用户可见的诊断（`Diagnostics.stopTimeouts`）。
2. **上界是第二道，不是主修**：主修是让网络前置阶段本身可取消且有上界（`core/ai/PreConnect.kt`，
   解析丢到 daemon 线程 + 100ms 轮询取消 + `PreConnectTimeoutMs` 5s）。抬高上界来「少触发」是禁的。
3. 被强收的那一轮**不许再写新增历史**（`abandonedTurn`，挡在会话写历史的唯一入口）。

## 后果

**为什么这不等于 0003 当年否决的那个「猜延时」**：

- 新一轮仍然排在 `runGate` 后面 —— 强制回 `Idle` 只放开**界面**，历史写入依旧串行，
  当年那条「旧轮把已撤回的回复 append 回来、把新一轮的 RUNNING 覆盖成 IDLE」的竞态没有回来；
- 卡住的那一轮从 `inFlight` **除名**而不是被忽略：不减就会永久「忙」，乱减就会「计数少一」，
  两种都是「永不收口」。成对判据由 `StopWatchdog` 的账目锁钉住（B 审补的第二条：
  迟到的定时器不许再减已经结束的任务）。
- 上界触发不再是静默的：诊断面板有一行中文说明（这一条正是 0003「允许排队 + 可撤回」没有的观测面）。

**代价（如实登记，不许读成已解决）**：

- 强制收口时僵尸协程仍活着且仍持有闸门：用户「能发」不等于「立刻在跑」，真正开始要等它放锁；
- 卡点若不响应取消（不响应的工具、`su` 授权弹窗、插件自带的传输实现），20s 只是止损线，
  主修对它无效；
- 被放弃那一轮若走到压缩提交（`replaceHistory`），历史仍会被整份改写 —— 闸门只挡新增，
  因为整份替换同时是修悬空 `tool_call` 的唯一通路。要闭合得先给「这一笔属于哪一轮」建模。

## 被否决的选项

| 选项 | 否决理由 |
|---|---|
| 给共享流式客户端加 `callTimeout` | 它覆盖整个调用（含读 SSE body），会把「模型思考三分钟」和「慢但持续有字节」的正常回合一起误杀（U57 验收点 V7 专钉这条） |
| 只加 `EventListener` 观测、不改行为 | 观测不改变「取消进不去」这个事实，用户照旧卡死 |
| 强制收口时直接强杀 / 重复调 `killTree` | 杀进程语义已在取消路径上；重复调用会把「被止损」伪装成「正常停止」 |
| 不设上界，让用户杀 App | 就是现状 |
