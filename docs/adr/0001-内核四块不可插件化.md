# 0001. 内核四块不可插件化

- **状态**：已接受
- **日期**：2026-10 之前（本文件为事后追记，依据 `AGENTS.md` §2 与现有实现）

## 背景

产品原则是「能力皆可插拔」：新增 provider 协议、压缩策略、存储后端、UI 面板，都应当是
「新增一个插件」而不是「改内核」。这条原则如果推到极致，会得出「连会话主循环也做成插件」
的结论——毕竟 `ContextStrategy` 已经能替换压缩策略了。

## 决策

只有四块留在内核，**不允许**插件化（`AGENTS.md` §2）：

1. 会话消息模型（`core/model`）
2. 会话主循环（`core/agent/AgentSession`）
3. 插件宿主：注册表 + `HookBus`（`core/plugin`）
4. 请求装配器与「缓存稳定前缀」契约（`core/agent` 的装配路径）

## 后果

**收益**：缓存前缀契约只有一个实现点，`RequestAssembler` 能对分段做确定性摘要；
插件 ABI 的边界因此清晰——插件只能通过 `ctx` 注册贡献点，不能改装配顺序。

**代价**：

- 主循环持续膨胀：`AgentSession.kt` 已达 **1638 行**，是仓库里最大的文件；
- 「加一个进行中的状态」只能改内核，于是出现 `_stopping` / `_compacting` / `pendingRuns`
  这类布尔量拼装（见 `docs/架构评估-2026-10.md` §3.2）；
- 内核里的行为（停止、中断、压缩）难以单测，因为一切都耦合在同一个类里。

**缓解**：拆分必须**保持行为逐字节一致**（评估 A5：抽 `TurnState` / `InterruptSanitizer` /
`QueueDrain`），且不得借拆分之机改语义。

## 被否决的选项

| 选项 | 否决理由 |
|---|---|
| 把主循环做成 `ContextStrategy` 一类的插件 | 历史写入、工具配对修复、取消收尾必须单线程串行；插件化后无法保证「同一会话只有一个写者」 |
| 把消息模型做成可替换序列化 | 会话日志是持久化格式，换实现会让旧 `.jsonl` 不可读；且请求前缀字节稳定依赖模型字段顺序 |
| 让插件参与装配顺序 | 装配顺序进入缓存前缀，任何第三方插件都能破坏命中率，且问题极难定位 |
