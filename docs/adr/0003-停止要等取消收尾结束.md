# 0003. 停止要等取消收尾结束

- **状态**：已接受
- **日期**：2026-10-26（PR #17 引入；本文件为该决定的定稿记录）

## 背景

用户点「停止」时，`job.cancel()` 只是**投递取消信号**：容器里的命令要等信号送达、
看门狗 TERM→KILL 走完才真正返回；随后还要修复工具配对（悬空 `tool_call` 会让下一回合请求
被 provider 直接拒绝）并落盘。

原实现 `abort()` 同步把状态置为 `IDLE`，于是出现两个真实故障：

1. 界面立刻放行下一条消息 → 新一轮与**仍在收尾**的旧轮同时改 `_messages`
   （旧轮把已撤回的回复 append 回来、把新一轮的 RUNNING 覆盖成 IDLE）；
2. 收尾还没跑完，用户就以为「已经停了」。

## 决策

- `abort()` **不**同步置空闲，只置 `stopping` 并取消 Job；真正回到 `IDLE` 发生在
  `launchSerial` 的完成回调（`pendingRuns` 归零）里，即「杀进程 + 修配对 + 落盘」全部结束之后；
- 停止期间 `_status` 仍为 `RUNNING`（对外表现为忙），界面把停止键换成转圈；
- 停止期间**不禁止发送**：消息进 `FOLLOW_UP` / `STEER` 队列，由 `drainQueueAfterStop()`
  在收尾结束后接成新回合。历史写入始终由 `runGate` 串行。

## 后果

**收益**：历史写入只有一个写者；「停止 → 抢发」竞态从机制上消失。

**代价**：

- 多了一个必须与 `_status` 保持一致的状态（`stopping`），这正是
  `docs/架构评估-2026-10.md` §3.2 指出的「布尔量拼装」问题；
  **本 ADR 是 A1（显式状态机）的直接动因**；
- `stopping` 本身没有上限：如果某个工具在 `NonCancellable` 里不响应取消（违反
  `代码规范.md` §5），界面会一直「正在停止」。当前的处理是「允许排队 + 可撤回」，
  不额外加超时——加超时等于允许新一轮与收尾并发，会把已解决的问题重新引回来。

## 被否决的选项

| 选项 | 否决理由 |
|---|---|
| 保留「同步置空闲 + 后续靠闸门排队」 | 界面会显示空闲，用户在此期间的操作语义全是错的（能编辑、能撤回、能压缩） |
| 加固定延时兜底（如 5s 后强制置空闲） | 延时是猜的：容器冷启动时杀进程可能超过 5s，猜短了重演竞态，猜长了用户干等 |
| 停止期间禁用输入 | 工具不响应取消时，用户被永久锁死在输入框外，连排队与撤回都做不到 |
